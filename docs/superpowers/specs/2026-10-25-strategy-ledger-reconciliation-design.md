# 전략 원장 대사 알림 설계

작성일: 2026-10-25 · 상태: 사용자 승인 대기

## 의도

2026-10-25부터 각 전략은 자기 원장(`trading.cycle_position`의 `usd_deposit`·`holdings`) 안에서만 매수한다(`StrategyLedgerBudget`, `2026-10-24-strategy-own-ledger-budget-design.md`). 원장이 실계좌와 어긋나면 매수가 부당하게 거절·승인되거나, 매도가 브로커에서 거절된다(`APBK0988`). 이 도구는 **앞으로 생길 괴리를 실제 피해 전에 관리자에게 알리는 대비용 감지기**다. 현재 의심 계좌는 없다(사용자 확인).

## 목표 / 비목표 / 반목표

- 목표: 실계좌 보유량이 전략 원장 합보다 적은 계좌·종목을 하루 1회 관리자 텔레그램으로 알린다. MOCK 계좌는 원장 불변식 위반(음수)을 알린다.
- 비목표(1차 범위 밖): 보정 기능, 관리자 화면, 현금(예수금) 경보, 종가 대사(2026-09-08 VR 사례), 코인 계좌. 알림이 실제로 울리기 시작해 조사가 필요해지면 화면·보정을 별도 설계로 붙인다.
- 반목표:
  - 매매 경로에 들어가는 것. KISTA는 실계좌 잔고를 매매 판단에 쓰지 않는다. 대사 결과는 주문 생성·원장 예산에 절대 반영하지 않는다.
  - 정상일 때 울리는 것. 사용자가 KISTA 밖에서 같은 종목을 들고 있다고 매일 알림이 오면 실패다.
  - 원장을 자동으로 고치는 것.

## 배경 사례 (운영 DB 읽기 전용 조회, 2026-10-25)

- TEST(MOCK) PRIVACY SOXL: 10-17 KST 스냅샷에서 `usd_deposit = -126.71`이었고, 10-20 매도로 회복했다. 최신 값은 `545.96 / 102주`다. 원장 증감은 orders 체결과 센트 단위까지 일치한다. 따라서 이 사례는 원장·체결 괴리가 아니라, 예산 규칙이 생기기 전에 생긴 초과 매수다. MOCK 불변식 검사(음수)는 이런 경우를 잡는다.
- 2026-09-08 VR 종가 오염: Toss 종가가 하루 어긋나 `closing_price`, 사이클 금액, V까지 연쇄 오염됐다. 종가 대사는 이번 범위가 아니다(비목표).
- 기존 `ManualTradeCorrectionService`는 빠진 체결을 덧붙이는 방식만 지원한다. 감지 전용인 1차는 이 서비스를 쓰지 않는다. 경보가 나면 관리자가 기존 admin 정정 API로 처리할 수 있다.

## 결정 사항

### 검사 규칙

대상 전략: 삭제되지 않은 전략 중 최신 사이클이 종료되지 않은(`strategy_cycle.end_date IS NULL`) 전략. 전략 `status`(ACTIVE·PAUSED)는 가리지 않는다 — PAUSED 전략도 주식을 들고 있으므로 빼면 원장 합이 과소가 돼 미탐이 난다(내 판단).

1. **실계좌(MOCK 외, 코인 계좌 제외 — `Broker.market` 기준, 메리츠 포함) 보유량 부족**: 종목(`StrategyTicker`)별로 `원장 합 = Σ 해당 종목 전략들의 최신 cycle_position.holdings`(DCA 포함)를 구한다. `브로커 보유량`은 `PortfolioPort.getPresentBalance(brokerRef).items()`의 종목별 `holdings`(총 잔고수량)다. 계좌당 1회 호출로 전 종목을 받는다. 종목마다 부르는 `SellableQuantityPort` 대신 이것을 쓰는 이유는 호출 수다(내 판단). 두 포트 모두 미체결 매도를 빼지 않은 총 잔고수량이다 — 메리츠 판매가능수량이 `seln_able_dqty`(순수량)를 반환하던 버그는 이 설계 중 발견해 `rmnd_dqty`로 고쳤다. 경보 조건은 `브로커 < 원장 합` 하나다.
2. `브로커 > 원장 합`은 무시한다. 사용자가 KISTA 밖에서 같은 종목을 보유할 수 있기 때문이다(사용자 확인).
3. **MOCK 계좌**: MOCK 잔고는 `MockBrokerAdapter`가 원장 합으로 만들기 때문에 바깥 기준이 없다. 대신 전략별 최신 `usd_deposit < 0` 또는 `holdings < 0`이면 경보한다.
4. 현금은 1차에서 검사하지 않는다. 브로커 주문가능금액(`MarginPort.getUsdBuyableAmount`)은 예수금이 아니라 미결제 대금·환전·수수료·미체결 예약의 영향을 받아 노이즈가 크다.

### 실행 시점

- 마감 배치와 그 리포트가 끝난 뒤, 개장 배치(22:00 KST) 전에 하루 1회 돌린다. 기본값은 화~토 09:00 KST다(builder 결정 — 아래 참고).
- 미종결 주문이 있는 계좌를 건너뛰는 규칙은 두지 않는다. 총 잔고수량은 미체결 매도에 영향받지 않고, 미체결 매수는 아직 원장에도 반영되지 않았기 때문이다. 마감 리포트 뒤에도 체결 반영이 빠졌다면 그것이 곧 잡아야 할 괴리다(내 판단 — 좀비 PLACED 주문 때문에 계좌가 영구히 조용히 건너뛰어지는 것을 피한다).

### 알림

- 경로는 `TradingErrorReportPort.reportError(Exception)`이다. 기존 trading-core 관리자 운영 알림을 재사용한다.
- 하루 1회 배치이므로 별도 중복 제거는 두지 않는다. 재기동 등으로 같은 날 다시 돌면 같은 경보가 한 번 더 갈 수 있는데, 감지 도구로서 무해하다(내 판단). `TradingBatchResumer` 재개 대상에도 넣지 않는다 — 놓친 날은 다음 날 검사가 잡는다.
- 메시지에는 계좌 nickname, 종목, 브로커 보유량, 원장 합, 전략별 holdings 내역을 담는다. 계좌번호는 넣지 않는다(마스킹 규칙).
- 정상이면 아무것도 보내지 않는다.

### 실패 처리

- 한 계좌의 브로커 조회 실패는 그 계좌만 건너뛰고, 다른 계좌 검사는 이어간다. 브로커 조회 실패는 일반 오류 알림으로 보낸다. 대사 경보와는 문구로 구분한다.

## 배치 위치 (원칙만, 세부는 builder)

- trading-core `com.kista.tradingcore.trading` 모듈 안에 둔다. 원장·전략·주문 소유자이고, broker 포트를 이미 소비한다.
- 스케줄러는 `adapter/in/schedule`, 대사 로직은 `application/service`에 둔다. 계좌 간 비교 규칙은 순수 함수로 분리해 단위 테스트한다.
- `SchedulerLockService`로 다중 기동 이중 실행을 막는다. 기존 스케줄러 패턴을 따른다.
- 이 서비스가 브로커 잔고를 읽는다는 사실과 "결과를 매매 경로에 쓰지 않는다"는 원칙을 모듈 문서(`docs/agents/modules/tradingcore/trading.md`)에 한 줄 남긴다.
- `docs/agents/scheduler-time-table.md`에 실행 시각을 추가하고, `flows.yml`에 흐름을 추가한다(드리프트 규칙).

## builder에게 맡긴 것 / 내 판단으로 정한 것

- 실행 시각 화~토 09:00 KST: 내 판단이다. 마감 리포트(대략 05~06시 KST) 이후, 22:00 이전이면 어느 시각이든 무방하다.
- 대상 전략 범위(PAUSED 포함), `PortfolioPort` 총 잔고 사용, 미종결 주문 건너뛰기 없음, 중복 제거 없음: 내 판단이다.
- 경보 예외 타입, 메시지 문구, 클래스 이름은 builder가 정한다.
- builder 확인 사항: 브로커별 `getPresentBalance` 구현(KIS·Toss·메리츠)이 `Item.holdings`에 판매가능이 아닌 총 잔고수량을 담는지 확인한다(메리츠는 `rmnd_dqty`여야 한다). 아니면 그 어댑터를 고치는 것까지 범위에 넣는다.
- 정수 주식만 대상이다(`Item.holdings`가 int). 코인 계좌는 제외한다.
