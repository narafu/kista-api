# 05 단계 M(한 애플리케이션 통합, 2 role) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 루트 `:api`와 `:trading-core`를 한 Spring 컨텍스트(`ApiApplication`, jar 하나)로 합치고, 같은 jar를 `kista.role=web|worker`로 두 role로 띄울 수 있게 한다. 전환 배포는 하지 않는다.

**Architecture:** root가 `implementation(project(":trading-core"))`로 trading-core를 품는다. `ApiApplication`이 `com.kista.api`·`com.kista.tradingcore`를 스캔하고, 중복 빈과 프로세스 경계용 Redis 스트림 경로를 지운다. 두 Flyway 이력은 shared의 마이그레이터 하나가 순서대로 적용한다. role 경계는 기존 `@ConditionalOnWorkerRole`과 새 서블릿 필터 `RoleRoutingGuard`가 맡는다. trading-core 테스트는 자기 서브프로젝트에 남고, 테스트 전용 `TradingApplication`과 테스트 전용 `application.yml`로 지금과 같은 컨텍스트를 띄운다.

**Tech Stack:** Java 25, Spring Boot 4.1.1, Spring Modulith, Flyway, Gradle 멀티프로젝트, bats.

**Spec:** `docs/superpowers/fable-review/guides/05-modules-and-processes.md` 4-1절(M1~M14) → 13절 → 14-2·14-4절 → 15절 순으로 뒤가 우선. 재측정 결과는 이 계획의 "재측정" 절이 최신이다.

## Global Constraints

- **마이그레이션 파일을 하나도 추가·수정하지 않는다**(14-2 M5). 최종 확인: `git diff main --stat -- '*.sql'`가 비어 있다.
- 패키지·클래스 이름을 바꾸지 않는다(M8, EPR `listener_id`가 FQCN). 지우는 것만 지운다.
- `spring.application.name`은 `kista-api`. `management.metrics.tags.role=${kista.role}`를 추가한다.
- `kista.role` 기본값은 `${KISTA_ROLE:web}`(15절 P4 후속). prod는 `${KISTA_ROLE}`(기본값 없음) 그대로. 테스트는 shared `application-test.yml`에 `kista.role: all`.
- `@Primary`·`@Qualifier`·`@Lazy`로 충돌을 덮지 않는다(14-4). 구현 하나짜리 인터페이스를 만들지 않는다.
- 동작 보존: 응답 상태·본문·주문 값이 바뀌는 테스트 기대값 변경 금지. 예외는 구조 단언(저장소 수·모듈 수·빈 0개 단언)과 `app_error_logs` caller 값.
- 가드: FQCN·패키지 문자열·개수는 고친다. 규칙의 뜻(의존 방향, 시간 기준)은 약화하지 않는다(로드맵 9-3).
- `flows.yml`의 `code:`는 클래스를 지우는 그 커밋에서 고친다.
- 서브에이전트는 `git add`/`commit`을 하지 않는다(컨트롤러가 리뷰 뒤 커밋). 작업 디렉토리는 `/Users/phs/workspace/kista/kista-api`, 브랜치 main(M 브랜치 없음 — 사용자 결정 2026-11-20). M이 끝나 전환일이 정해질 때까지 main을 push하지 않는다.

- **D1 trading-core 테스트의 기동 클래스**: `TradingApplication`을 trading-core **test** 소스셋(같은 패키지 `com.kista.tradingcore`)으로 옮기고, trading-core main `application.yml`을 `trading-core/src/test/resources/application.yml`로 옮긴다(테스트에 필요한 키만 남긴다). 테스트 54개와 `SchedulerLockService*Test`의 참조는 그대로 컴파일된다. 대안(테스트 54개를 root로 이동, 54곳에 `@ContextConfiguration`)보다 diff가 가장 작다.
- **D2 search_path(M4)**: 바꾸지 않는다. 합친 `application.yml`은 root 값 `SET search_path TO finance, kista_ref, public`을 쓴다. main SQL은 P3로 전부 스키마 한정(가드 `NativeSqlSchemaQualifiedTest`), 엔티티는 전부 `@Table(schema)`, EPR은 `spring.modulith.events.jdbc.schema: public`, 락 테이블은 `kista.scheduler-lock.table`로 한정돼 운영 경로가 search_path에 기대지 않는다. root 테스트의 미한정 SQL은 지금 값 그대로 돈다. trading-core 테스트는 D1의 테스트 yml이 `trading, trading_ref`를 유지한다.
- **D3 Flyway 2벌(M5)**: Flyway 빈을 두지 않는다. shared에 `FlywayMigrationInitializer` 빈 하나를 두고, 그 전략이 `kista.flyway.migrations` 목록을 순서대로 migrate한다. Boot 자동구성은 `spring.flyway.enabled: false`로 끈다. `FlywayMigrationInitializer` 타입이라 Boot의 DB 초기화 의존 감지기가 JPA를 그 뒤로 미룬다(빈 DB 기동으로 확인). trading-core 테스트 yml은 trading 한 항목만 둔다.
- **D4 `RoleRoutes`(M10)**: 경로 표를 따로 만들지 않는다. `RoleRoutingGuard`가 요청마다 `RequestMappingHandlerMapping`으로 핸들러를 찾고, 핸들러 클래스가 `com.kista.tradingcore.` 패키지이거나 `@ConditionalOnWorkerRole`이 붙어 있으면 엔진 경로로 본다. Caddy 일치 검증은 기존 `CaddyRoutingTest`가 계속 한다.
- **D5 탈퇴 cascade 실행 위치**: 14-2 M9대로 스트림 경로를 지우면 `TradingUserCascadeListener`(미체결 주문 취소 = 브로커 호출)는 탈퇴 요청을 받은 web 프로세스에서 돈다. 1-1 원칙("브로커 호출은 worker만")과 어긋나지만 05 3절 P5·14-2가 정한 설계이고 탈퇴는 드물다. 바꾸지 않고 기록만 한다.
