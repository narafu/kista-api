# 12. 기능 검토: 유지가 애매한 것, 보완할 것, 추가할 것

작성 2026-11-13 (Fable). 근거는 `findings/16-feature-inventory.md`(엔드포인트 176개·스케줄 진입점 23개·알림 28종 전수, 운영 DB 읽기 전용 조회, kista-ui 호출처 grep)와 `findings/15`·`18`. 기준 커밋 `1db0d8db1`.

이 지침서는 다른 지침서와 성격이 다르다. 기능을 남길지 지울지는 사용자가 정한다. Fable은 기능마다 드는 비용과 운영에서 쓰인 흔적을 붙이고 권고를 낸다. 결정이 난 항목만 실행 태스크가 된다(6절).

## 0. 전제: 운영에서 실제로 쓰이는 범위

2026-11-13 운영 DB 기준이다.

- 사용자 2명(ADMIN 1, USER 1). 계좌 8개와 활성 전략 8개는 전부 ADMIN 것이다. USER는 가계부만 쓴다.
- 활성 전략: BINANCE×DCA 1, KIS×INFINITE 1(KIS는 삭제 결정됨), MERITZ×VR 1·PRIVACY 1, MOCK×4종 각 1. 최근 30일 주문 1,132건 중 529건(47%)이 MOCK이다. 운영 환경이 모의 검증도 겸한다.
- 전략은 누적 71개 중 63개가 삭제됐고 최근 30일에 22개가 만들어졌다. 운영자가 등록과 삭제를 반복하며 쓴다.
- 접근 로그와 메트릭 수집이 없다. 통계·백테스트·포트폴리오·벤치마크 조회처럼 DB에 쓰지 않는 기능은 **쓰이는지 알 수 없다.** 아래 표의 "흔적 없음"은 "안 쓴다"가 아니라 "측정할 수 없다"는 뜻이다.

kista-ui 화면 사용 여부는 fable-ui에 묻지 않고 kista-ui 소스에서 호출처를 grep해 확인했다(수정 없음). ui가 호출하는데 API에 없는 경로는 0건, API는 있는데 ui 호출이 없는 것은 서버 간 내부 30개를 빼고 14개다.

## 2. 뿌리 결정 D0: 다른 사용자를 받을 것인가

가장 많은 코드가 이 질문 하나에 달려 있다. 지금 KISTA에는 "여러 사용자를 받는 서비스"를 위한 골격이 있고, 운영에서는 그 골격이 거의 쓰이지 않는다.

| 골격 | 규모 | 운영 흔적 |
|---|---|---|
| 가입 승인 흐름(PENDING·REJECTED, 텔레그램 승인 버튼, 상태 SSE, 재신청 쿨다운, 거절 사유 마스킹) | 26파일 약 1,600줄(파일 전체 기준, 다른 로직 포함) + ui `/pending`·`/rejected`·`/admin/pending` | `approvalRequired=false`로 꺼져 있다. 승인 1건(2026-06-17) |
| 관리자 런타임 설정(브로커·전략 종류 허용, 전략 필드별 허용값·기본값·변경 가능 여부) | 1,171 / 1,583, 같은 트리를 5곳에 선언(약 620줄) | 변경 누적 20회. 지금 값: KIS·업비트 비활성, 나머지 전부 활성 |
| 관리자의 사용자·계좌·전략·주문 조회와 정지·재개 | admin 모듈의 조회 부분 | 정정 4건, 마지막 2026-07-02 |
| 감사 로그 | 3파일 + 호출 16곳 | 37행, 관리자 1명 |

선택지와 결과:

- **(가) 받는다 — 지금 전제 유지.** 골격을 남긴다. 그러면 지금 꺼져 있는 승인 흐름의 구멍부터 막아야 한다: PENDING 사용자가 로그인 때 받은 토큰으로 인증 경로를 전부 호출할 수 있다(13의 보안 절, 결함). 런타임 설정은 남기되 5중 선언을 줄인다(13).
- **(나) 받지 않는다 — 본인·가족용으로 확정.** 승인 흐름, 전략 필드별 허용값 정책, 관리자의 타인 계좌 조회·정정, 감사 로그를 지운다. 가입은 `ADMIN_KAKAO_IDS` 같은 허용 목록으로 막는다. 브로커·전략 종류 켜고 끄기만 설정으로 남긴다. main 약 2,500~3,500줄과 그 테스트, ui 화면 6~7개가 사라진다(추정. 결정되면 전수표를 먼저 만든다).

권고: **(가)**. 토스 주문을 "대중적인 증권사라 연결을 남긴다"고 정한 것(04, 2026-11-12)은 다른 사용자를 전제로 한 결정이다. 다만 (가)를 고르면 "실제 두 번째 매매 사용자가 생기기 전에는 이 골격에 새 기능을 얹지 않는다"를 규칙으로 둔다. 지난 90일 동안 런타임 설정 18커밋, 수동 보정 29커밋처럼 쓰이지 않는 골격에 손이 계속 갔다.

## 3. 유지가 애매한 후보의 판정

### 3-1. PRIVACY·FIDA 연동 — 유지

메리츠 실계좌에서 돌고 있다(30일 주문 56건). FIDA가 KISTA로 push하는 구조라 KISTA 쪽 외부 호출 비용은 0이고, fida는 별도 레포 유지로 결정됐다. 지울 이유가 없다.

보완할 점 하나: 운영자가 기준표를 90일 동안 11번 손으로 고쳤다(감사 로그 `PRIVACY_BASE_UPDATE`). 손으로 고쳐야 하는 원인이 FIDA 쪽 수집 오류인지 KISTA 쪽 수신 검증인지 확인해 원인을 없앤다(4절 B5).

### 3-2. 백테스트 — 유지, 결함 하나 고친다

- VR·INFINITE·PRIVACY를 지원하고 DCA는 지원하지 않는다(`BacktestService.java:92-94`).
- `FillSimulator`를 MOCK 브로커가 함께 쓴다. 백테스트를 지워도 이 클래스는 남는다. 03 T7이 실행 루프 3벌을 하나로 합치므로 유지 비용은 줄어든다.
- **결함**: `AlpacaCandleAdapter.java:64`가 페이지네이션을 구현하지 않았다. 긴 기간을 요청하면 일봉이 잘려도 오류 없이 결과가 나온다. 수익률이 조용히 틀리는 종류라 고친다(4절 B1).
- DCA 백테스트를 추가할지는 5절 A2.

### 3-3. 벤치마크 — ETF 비교는 유지, 주택은 삭제 권고 (D1)

`api.benchmark` 2,437줄은 두 덩어리다.

|---|---|---|
| main | 24파일 약 1,059줄 | 나머지 약 1,380줄 + trading 쪽 `InvestmentPointsQueryService` 264줄, 내부 API 2개 |
| 스케줄러 | 3개(주간 2, 월간 전체 재수집 1) | 1개(매일 종가) |
| 테이블 | `housing_price_indices` 22,227행, `housing_benchmark_prices` 2,236행 — 운영 DB 전체 행의 40% | `market_index_prices` 21,891행 |

| 매매와의 관계 | 없음(내 투자 수익을 아파트 가격과 견준다) | 있음(내 전략을 QLD 같은 ETF 보유와 견준다) |

주택 쪽은 매매 서비스의 핵심과 닿는 곳이 없고, 조회 흔적을 확인할 수 없다. 사용자가 이 화면을 실제로 본다면 유지한다. 유지 비용 자체는 낮다(90일 커밋 14개, 오류 0).

삭제를 고르면 사라지는 것: 주택 파일 24개와 테스트, 스케줄러 3개, 수동 트리거 엔드포인트 3개, 테이블 2개(contract 단계에서 drop), `BenchmarkAlertRaisedEvent`의 주택 발행처 2곳, ui `/stats/benchmark`의 주택 부분(fable-ui에 전달).

### 3-4. 공포탐욕지수·코인 시장 지표

- **공포탐욕지수는 유지.** 운영의 DCA 조건 9개 중 2개가 `FEAR_GREED`를 쓴다. 매매 판단의 입력이다.
- 수집기가 두 벌이다: root `CnnFearGreedAdapter`·`CryptoFearGreedAdapter`(대시보드용 스냅샷)와 trading-core `CnnFearGreedIndexAdapter`·`CryptoFearGreedIndexAdapter`(DCA 조건용). 같은 외부를 두 프로세스가 각자 부른다. 05 통합 뒤 하나로 합친다(4절 B4).
- **코인 시장 지표는 유지 권고(D2).** 919줄이고 요청 때 외부 7곳을 부른다(10분 캐시). 비인증 공개 엔드포인트다. 대시보드 위젯 하나의 값으로는 비싸지만 코인 DCA를 실계좌로 돌리는 중이고 90일 커밋이 45개(공포탐욕 포함)로 지금도 손보는 기능이다. 화면을 안 본다면 삭제 후보 1순위다(record 31개, 외부 어댑터 6개, Config 6개가 함께 사라진다).
- 업비트 브로커를 지워도(04) 이 기능의 `UpbitMarketDataPort`(김치 프리미엄 계산)는 남는다. 04 단계 A의 삭제 범위에서 `stats/adapter/out/upbit`를 빼야 한다.

### 3-5. 가계부 — 유지

매매와 무관한 도메인이 root main의 30%(5,024줄), 엔드포인트의 24%(42개)를 차지한다. 그러나 사용자 2명이 실제로 쓰는 유일한 기능이고(30일 거래 39건, 자산 기록 44건) 90일 커밋 12개로 가장 안정적이다. 다른 모듈과의 결합도 거의 없다(외부에서 import하는 main 파일 3개).

- 별도 서비스로 떼는 안은 기각한다. 배포물·DB·인증을 하나 더 운영하는 비용이 5,000줄을 같이 싣는 비용보다 크다.
- 그룹 공유(share/unshare 14개 엔드포인트)는 마지막 쓰기가 2026-08-22지만 쓰이지 않는 것이 아니다. 거래 804건 중 445건이 그룹에 속해 있다. 한 번 만든 그룹이 계속 쓰이는 구조다.
- 코드 비대는 13의 가계부 절이 다룬다(5개 애그리게이트가 같은 뼈대 3,093줄).

### 3-6. MOCK 브로커 — 유지

339줄과 분기 31줄로 운영 주문의 절반을 만든다. 새 전략·새 공식을 실계좌 전에 운영 환경에서 돌려 보는 유일한 수단이다. 비용 대비 가치가 가장 높은 기능이다.

### 3-7. 수동 체결 보정 — 유지하되 동결 권고 (D3)

592줄, ui 화면 없음, 누적 사용 2건(마지막 2026-07-02), 그런데 90일 커밋이 29개다. 쓰지 않는 기능을 다른 변경에 맞춰 계속 고치고 있다.

지우지 않는 이유: 증권사 체결을 놓쳐 원장이 어긋났을 때 원장을 고치는 검증된 경로가 이것 하나다. 없으면 운영 DB의 `cycle_position`을 SQL로 직접 고쳐야 하고, 그 값으로 다음 주문이 계산된다.

동결의 뜻: 새 기능·새 전략 종류를 추가할 때 보정 경로의 지원을 넓히지 않는다. 지원하지 않는 조합은 지금처럼 거절한다(`ManualTradeCorrectionService.java:79` 방식). 06의 배치 재설계 뒤 "마감 리포트를 다시 돌리면 놓친 체결이 반영되는가"를 확인하고, 된다면 그때 삭제를 다시 본다.

## 9. 하지 말 것

- 결정 없이 기능을 지우지 않는다. 표의 "삭제 권고"는 권고다.
- "흔적 없음"을 "미사용"으로 읽지 않는다. A1의 측정이 쌓이기 전에는 조회 전용 기능의 사용 여부를 알 수 없다.
- 삭제할 때 테이블을 같은 배포에서 drop하지 않는다(expand/contract).
- 운영자가 등록·삭제를 반복한 흔적(삭제 전략 63개, 삭제 MOCK 계좌 5개)을 정리 대상으로 보지 않는다. 11의 D1이 다룬다.
