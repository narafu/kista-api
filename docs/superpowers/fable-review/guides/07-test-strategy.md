# 지침서 07. 테스트 전략 — 규칙이 사는 층에서 한 번만 검증한다

작성 2026-11-12 (Fable). 근거 측정: `findings/04-test-bloat.md`(정적 집계, 테스트 미실행), `findings/05-frozen-decisions.md` S-50·S-51·C-47. 이 지침서는 지침서 01·02·03·06의 구조 변경이 끝난 모듈부터 적용한다.

## 0. 먼저 알아둘 한계

- 테스트는 480파일 76,693줄, `@Test` 3,728개다. main(약 55,500줄)의 1.4배다.
- **테스트만 손대서 줄일 수 있는 양은 5~8%(약 4,000~6,000줄)가 한계다.** 보호군(공식·원장·주문 안전·상태 전이·보안·아키텍처)이 약 22,000줄이고, 계층 간 의미 중복은 10~20%뿐이다.
- 더 큰 감량은 main이 줄면서 따라온다. KIS·업비트 삭제(04), 경계 코드 제거(05 단계 X), 스케줄러 통합(06), 인터페이스 제거(01)는 대응 테스트를 함께 지운다. 이 지침서는 그 뒤에 남는 테스트의 **모양**을 정한다.
- 따라서 목표는 줄 수가 아니라 다음 둘이다: 규칙 하나를 바꿀 때 고치는 테스트가 한 곳인 것, 단언 한 줄에 붙는 준비 코드가 짧은 것.

## 1. 현재 구조와 문제

1. **규칙이 mock 서비스 층에서 검증된다.** `StrategyServiceTest`(3,098줄, 150개)의 `register_*` 약 80개는 등록 정책(VR 램프·시드·부트스트랩·DCA·티커 규칙)을 검증하는데, 그 규칙을 가진 `domain/creation`의 테스트는 12개뿐이다. 서비스 테스트는 포트 20여 개를 mock하고 첫 테스트까지 338줄, `when(` 425회다. 단언 1개에 stub 약 20줄이 붙는다.
2. **준비 코드가 복제돼 있다.** `new Strategy(` 207회, `new Account(` 63회가 `TradingFixtures`를 우회한다. 이름이 같은 private 헬퍼(`strategy` 11곳, `account` 10곳, `order` 9곳…)가 파일마다 있다.
3. **WebMvc 슬라이스의 62%(241개, 2,349줄)가 응답 본문을 보지 않는다.** 그중 147개는 401/403/400/404 상태만 단언한다. 그런데 `@WebMvcTest`는 커스텀 `SecurityConfig`를 로드하지 않고 Boot 기본 Security로 돈다(`testing.md`). 엔드포인트별 401/403 테스트는 운영 보안 정책이 아니라 테스트 슬라이스의 기본 동작을 검증하고 있다.
4. **소유권·4xx 매트릭스가 모듈마다 반복된다.** Finance 서비스 5개에 `SecurityException` 단언 74회.
5. **왕복만 확인하는 영속 테스트.** DataJpa 44파일 6,185줄 중 단순 save/find 왕복이 섞여 있다. 스키마 일치는 `ddl-auto: validate`가 이미 본다.
6. **순수 배선 테스트** 약 25~30파일 2,500~3,500줄(추정): 위임만 하는 내부 컨트롤러·notifier·DTO `from()`.
7. `TradingServiceTest`(2,418줄, `when(` 407, `verify` 222 대 `assertThat` 6). 호출 순서가 곧 안전 속성이라 배선 테스트가 아니지만, 시나리오마다 같은 stub 묶음을 다시 쓴다.

## 2. 목표 구조

### 2-1. 테스트 종류는 넷, 각자 맡는 것이 다르다

| 종류 | 대상 | 협력자 | 검증하는 것 | 검증하지 않는 것 |
|---|---|---|---|---|
| **규칙 테스트** | 도메인·커널·판정 함수(순수) | 없음 | 입력 → 출력의 모든 경우. 표 기반(`@ParameterizedTest`)을 기본으로 | 호출 순서 |
| **흐름 테스트** | 서비스·단계 | 외부 경계만 mock(브로커, 알림, 시계). 같은 모듈의 도메인 객체·순수 협력자는 진짜를 쓴다 | 어떤 조건에서 무엇을 호출·저장·발행하는가, 실패 격리, 순서가 안전 속성인 곳의 순서 | 규칙의 경우의 수(대표 1개만 통과시킨다) |
| **저장 테스트** | Store(지침서 02) | 실 DB(`DataJpaTestBase`) | 직접 쓴 쿼리, 유일 제약, soft delete 필터, 암호화 컬럼, 동시성 | 필드 복사 왕복 |
| **계약 테스트** | 컨트롤러 + 전역 예외 처리기 | 서비스 mock | 요청 바인딩·검증 400의 종류별 1건, 응답 JSON 모양(`jsonPath`), 예외 → 상태·`code` 매핑 | 서비스 로직, 엔드포인트별 401/403 |

여기에 지금도 있는 구조 가드(ArchUnit·Modulith·컨텍스트 로드·`InternalApiContractTest`·OpenAPI 스냅샷)와 `*IT`가 더해진다. 줄 대비 가치가 가장 높으므로 줄이지 않는다.

### 2-2. 규칙을 아래로 내린다

- 서비스 테스트에서 "입력 X면 예외 Y" 형태의 테스트를 찾아, 그 규칙을 가진 순수 클래스의 표 기반 테스트로 옮긴다. 서비스 테스트에는 "규칙 위반이면 저장하지 않는다"를 보이는 대표 1건만 남긴다.
- 옮길 곳이 없으면(규칙이 서비스 메서드 본문에 인라인) **main을 먼저 고친다**: 규칙을 순수 함수·값 객체로 뽑고(지침서 03의 `StrategyKind.resolveCreation`, 지침서 06의 판정표가 그 예다) 테스트를 그쪽에 쓴다. 리팩토링 커밋과 테스트 이전 커밋은 분리한다.
- 순서: ① 순수 쪽에 표 기반 테스트를 추가한다 ② 변이 확인(규칙 한 줄을 틀리게 해 새 테스트가 실패하는지) ③ 서비스 테스트의 대응 항목을 지운다. 옮긴 항목의 대응표(옛 테스트명 → 새 표의 행)를 커밋 메시지 본문에 남긴다.

### 2-3. 준비 코드: 빌더 하나, 시나리오 헬퍼는 파일당 하나

- 도메인 객체는 `TradingFixtures`·`DomainFixtures`의 빌더로만 만든다. 테스트 파일의 `new Strategy(`·`new Account(`·`new Order(`·`new CyclePosition(`를 치환한다. 빌더에 없는 변형은 빌더에 `with*`를 추가한다(파일 안 private 래퍼를 새로 만들지 않는다).
- 큰 흐름 테스트는 stub 묶음을 "상황" 단위 헬퍼로 올린다: `givenActiveInfiniteCycle()`, `givenPlacedOrders(...)`처럼 읽히는 이름. 테스트 본문은 준비 3줄 이내 + 실행 + 단언이 되게 한다.
- 가드 신설(테스트 소스 대상 ArchUnit, `TradingCoreTestVendorModelTest`와 같은 방식): fixture 패키지 밖 테스트가 `Strategy`·`Account`·`StrategyCycle`·`CyclePosition`·`Order`의 생성자를 직접 호출하지 않는다. 대상 클래스의 테스트 자신(`StrategyTest` 등)은 예외.

### 2-4. 보안·오류 상태는 정책 테스트 한 곳

- 401/403(인증·역할)은 실제 `SecurityConfig`를 올리는 정책 테스트(`RootSecurityPolicyTest` 계열, 지침서 05 뒤에는 하나)가 **라우트 규칙 단위**로 검증한다: 공개 경로, 내부 토큰 경로, 관리자 경로, 그 밖의 인증 필요 경로에서 대표 URL 1개씩. 컨트롤러 슬라이스의 401/403 테스트는 지운다.
- 소유권 403은 규칙이다. 도메인(`account.verifyOwnedBy`, `OwnedStrategy.load`) 테스트 1곳과 예외 → 403 매핑(전역 처리기 테스트) 1곳이면 된다. 서비스마다 "남의 것이면 예외"를 반복하는 테스트는 그 서비스가 소유권 검사를 **호출한다**는 대표 1건으로 줄인다. Finance 5개 서비스는 표 기반 테스트 하나로 묶는다(서비스·메서드가 표의 행).
- 400(검증)은 DTO 제약마다 1건이 아니라, 컨트롤러마다 "검증이 켜져 있다"를 보이는 1건 + 직접 쓴 검증 로직(compact constructor의 IAE, 교차 필드 규칙)의 규칙 테스트.
- 404·409 등 예외 매핑은 전역 처리기의 `MAPPINGS` 표를 표 기반으로 1회 검증한다.

### 2-5. 저장 테스트의 기준

지운다: 엔티티를 저장하고 같은 필드를 읽어 비교하는 것만 하는 테스트. 남긴다: `@Query`·native query(soft delete 수동 조건 포함), 정렬·페이징·집계, 유일 제약 위반, `@Convert` 암호화, 낙관·비관 잠금, cascade 순서. Store 하나에 "직접 쓴 쿼리마다 1건 이상"이 기준이다.

### 2-6. 배선 테스트

지운다: 대상 메서드가 다른 빈 호출 한 줄이고 그 호출에 변환·분기·예외 처리가 없는 것. 지침서 01 단계 D가 위임 클래스를 지우면 대응 테스트도 같이 사라진다. DTO `from()` 필드 복사 테스트는 계약 테스트의 `jsonPath`와 OpenAPI 스냅샷(지침서 02 T1)이 대신한다. 조건부 마스킹 같은 로직이 있는 `from()`의 테스트는 남긴다.

### 이렇게 정한 이유

- 계층 중복은 원인이 아니다. "규칙을 한 층 위에서 검증"하는 위치 문제가 stub 비중을 만든다.
- mock을 줄이는 수단으로 서비스 테스트를 실 DB 통합 테스트로 바꾸지 않는다. 규칙이 내려가면 서비스 테스트에 남는 것은 흐름뿐이고, 흐름은 mock으로 충분히 짧다.

### 기각한 대안

- **포트별 인메모리 fake 도입**: stub 줄은 줄지만 fake 약 30개를 새로 쓰고 실제 Store와 동작을 맞춰 유지해야 한다. 지침서 02가 Store 모양을 바꾸는 중이라 두 번 쓰게 된다.
- **서비스 테스트를 `@SpringBootTest`로**: 실행 시간이 늘고, 로컬은 테스트 JVM이 한 번에 하나만 뜬다(`testJvmSlot`).
- **커버리지 기준 삭제(커버리지가 겹치는 테스트 제거)**: 주문 안전 군은 같은 줄을 다른 순서·실패 조건으로 지나는 것이 가치다. 줄 커버리지로는 구분되지 않는다.
- **변이 테스트 도구(PIT) 상시 도입**: 74,000줄에 돌리는 비용이 크다. 이전·삭제 시점의 수동 변이 확인으로 충분하다.
- **Testcontainers 전환**: 아래 재심.

- 위험 1: 규칙 이전 중 경우의 수가 빠진다. 대응표와 변이 확인이 막는다.
- 위험 2: 401/403 슬라이스 테스트를 지운 뒤 정책 테스트에 구멍이 있으면 실제 정책 회귀를 못 잡는다. **T3에서 정책 테스트를 먼저 보강**하고(라우트 규칙 전부 + 경로를 새로 추가했을 때 어느 규칙에 걸리는지) 그 다음에 지운다.
- 위험 3: 저장 왕복 테스트가 실제로는 직접 쓴 쿼리를 지나고 있을 수 있다. 파일 단위가 아니라 테스트 메서드 단위로 판정한다.

## 7. 하지 말 것

- 보호군의 단언·시나리오·`verify`를 지우지 않는다.
- 테스트를 지우면서 main을 같은 커밋에서 고치지 않는다(규칙 추출 리팩토링은 별도 커밋, 테스트가 초록인 상태에서).
- 통과시키려고 단언을 느슨하게 바꾸지 않는다(`isEqualTo` → `isNotNull` 등).
- 파라미터화를 위해 서로 다른 규칙을 한 표에 섞지 않는다. 표 하나는 규칙 하나다.
- `@Disabled`로 남기지 않는다. 지우거나 고친다.
- 줄 수 목표를 맞추려고 대상을 넓히지 않는다. 4절의 추정은 상한이 아니라 예상이다.
