# 주문 접수·상태 전이·취소·재주문·기록 테이블

배치 실행 순서는 workflow-batch.md.

### 미체결 주문 정리 · 재주문
- 전략 일시정지·삭제(`StrategyService`)와 계좌 삭제(`AccountOpenOrderCanceller` — 계좌의 전략마다 `StrategyStateWriter.pause` 후 정리)는 현재 사이클의 미체결 주문을 `OrderCancelService.cancelOpenOrders`로 먼저 취소한다(증권사 취소 HTTP는 트랜잭션 밖). 재시도로 풀릴 수 있는 취소 실패(`retryableFailedCount`)가 있으면 삭제를 막고, 자격증명 오류(키 만료·철회)로 못 취소한 건은 삭제를 막지 않는다. 정지 시 취소된 주문의 부분 체결과 `ALREADY_FILLED`로 PLACED에 남은 주문의 체결은 그날 마감 배치가 정지 전략도 리포트해 원장(`cycle_position`)에 반영한다(삭제된 전략·계좌·탈퇴 사용자는 원장이 soft-delete라 대상 아님).
- 재주문(`ReorderService`): 현재 사이클의 미체결(PLANNED·PLACED) 원본만 허용(체결분은 수동 체결 보정 대상)하며, leg 없는 과거 주문(`UNKNOWN` leg)은 "주문 구분이 없는 과거 주문은 재주문할 수 없습니다"로 거절한다(원본 leg를 복사하므로 열린 UNKNOWN 주문이 되살아나는 것을 막는다). 휴장일(판정 시각의 `DstInfo.nextTradeDate(now)` 거래일 기준 — 시점 조회 API도 같은 기준)·시점 가용성·재주문 거래일=현재 거래일 검증을 원본 취소보다 먼저 수행해 검증 실패 시 원본이 취소된 채 남지 않게 하고, 증권사 호출은 트랜잭션 밖·DB 기록은 건별 짧은 트랜잭션으로 처리한다. IMMEDIATE는 PLANNED로 먼저 저장(id=멱등키)한 뒤 `OrderSubmitter`로 선점·접수한다 — 저장 실패면 증권사에 보내지 않고, 결과 불명은 SUBMITTING으로 응답한다. 선점 오류로 PLANNED(IMMEDIATE)가 남으면 마감 배치가 나중에 접수하지 않도록 취소하고 CANCELLED로 응답한다.
- **취소 직후 체결 기록**: 증권사 취소가 확정(`CANCELLED`·`ALREADY_CANCELED`)되면 `markCancelled` 커밋 뒤 트랜잭션 밖에서 `CancelledOrderFillRecorder.record`가 (거래일, 종목) 단위로 체결을 조회해 외부 주문번호로 거른 합산(수량·평균가)을 `OrderCancelStateWriter.recordCancelledFill`로 CANCELLED 주문에 기록한다(`OrderCancelService` 일괄·단건, `ReorderService.cancelSource`; PLANNED 취소는 증권사 미접수라 조회 없음). 조회 실패는 fail-open(`BrokerCallGuard.tryGet`, 값 null = "모름", warn 로그만 — 취소 결과 불변). 재주문 사전검사(`ReorderService`)는 PLACED BUY 원본의 현재 체결량을 조회해 환급분을 `price × (quantity − 체결량)`으로 잡고 조회 실패 시 재주문을 거부한다(fail-closed, 아직 아무것도 취소하지 않아 부작용 없음). `ReorderBuyBudgetService`(경고용)는 종목당 1회 조회하고 실패하면 전액 환급으로 본다. 이 기록분이 마감 리포트 전까지 원장 예산(`StrategyLedgerBudget.remaining`)·인출 가능액에 반영된다. 한계: 취소 처리 중(메리츠 ≈650ms) 들어온 체결이나 메리츠 history 반영 지연은 직후 조회에서 빠질 수 있고, 마감 리포트가 같은 주문을 체결로 덮어써 원장은 맞춰진다(미검증 — 실계좌 필요).
- **접수 선점(SUBMITTING)** (spec `docs/superpowers/specs/archive/2026-10-16-order-submission-claim-design.md`): 증권사 접수는 배치·수동 실행·재주문 즉시 접수 모두 `OrderSubmitter` 한 경로다 — 건마다 HTTP 직전 `markSubmitting`(PLANNED→SUBMITTING, 행 잠금)으로 선점하고, 선점 경합(그 사이 취소·삭제·재캡 취소)이면 HTTP를 보내지 않는다. 접수 성공은 `markPlaced`(SUBMITTING→PLACED), **확정 거절만** `markFailed`(SUBMITTING→FAILED — 판정 SSOT `BrokerApiException.isRejection`: 송신 전 실패·증권사 응답 거부·자격증명/토큰 한도 예외), 결과 불명(I/O·타임아웃·EGW00201 외 KIS 5xx·KIS 2xx 본문 없음·Toss 409 `request-in-progress`)과 PLACED 기록 실패는 SUBMITTING 유지 + 관리자 알림. 선점 직후 인터럽트는 송신 전이라 FAILED, 선점 자체의 일시 DB 오류는 그 주문만 PLANNED로 두고 건너뛴다(`[선점 실패]` 알림). 같은 잔류 주문의 `[접수 결과 불명]` 대사 알림은 프로세스당 1회. SUBMITTING은 재접수·재캡·일괄 삭제 대상이 아니고, 슬롯 점유·BUY/SELL 예약 합계에는 포함된다(BUY는 증권사 차감 여부 불명이라 보수적 이중 차감). 접수 경로 진입 시 `OrderSubmissionReconciler`가 잔류분을 대사한다 — 선점 2분 미만은 다른 스레드 접수 중일 수 있어 무시, Toss는 2~9분 창에서 같은 멱등키(`clientOrderId`=주문 id)로 재요청해 원 주문번호로 PLACED(거절이면 FAILED), KIS·창 밖은 `[접수 결과 불명]` 알림 후 런북 정정. 리포트 시점 잔류는 `[접수 결과 불명 — 리포트 제외]` 알림(리포트는 PLACED만 매칭). 실계좌 미검증: Toss 실제 멱등 재반환, KIS 오류 응답 본문 형태별 분류.
  - **잔고·수량 부족 분류(BUY·SELL 공통)**: 확정 거절 중 KIS `msg_cd=APBK0988`·Toss HTTP 422 `error.code=insufficient-buying-power`(BUY)·`insufficient-sellable-quantity`(SELL)는 `BrokerApiException.isInsufficientFundsRejection`이 분류하고 `OrderSubmitter`가 방향과 무관하게 `Outcome.INSUFFICIENT_FUNDS`로 돌려준다. `TradingOrderExecutor`가 접수 패스당 전략·방향별로 `InsufficientBalanceEvent`(`direction` 필드, 옛 EPR 행의 null은 BUY) 1건씩(사용자 알림 — SELL은 "판매 가능 수량 부족")을 모아 내고 관리자 알림은 내지 않는다(주문은 FAILED, 일부 접수 여부도 같은 방향 기준, DCA는 `DcaExecutionRecorder.recordOrderRejected`로 ORDERED→SKIPPED — SELL은 `INSUFFICIENT_HOLDINGS`). Meritz와 다른 코드는 분류하지 않고 기존대로 관리자 알림 + FAILED.
- **PLANNED 상태 전이 경합**: `OrderPort.markSubmitting`·`cancelPlanned`(PLANNED 전제)와 `markPlaced`·`markFailed`(SUBMITTING 전제)는 행 잠금 + 최신 상태 재조회(`flush` 후 `refresh(PESSIMISTIC_WRITE)` — 같은 트랜잭션에서 먼저 읽은 스냅샷을 믿지 않는다) 후 전제 상태일 때만 전이하고, 아니면(취소·삭제·이미 접수) `OrderStateConflictException`을 던진다. `deletePlannedByCycleAndDate`는 단일 `DELETE ... WHERE status='PLANNED'`문(잠금 대기 후 재평가 — 파생 delete의 SELECT→id별 DELETE는 그 사이 PLACED가 된 행까지 지운다)이고 실제 삭제 건수를 반환한다. 배치 접수(`OrderSubmitter`)는 선점 뒤 `markPlaced` 경합(방어용 — 정상 경로에선 선점이 막는다) 시 증권사 주문을 즉시 취소(실패 시 `[취소 경합]` 관리자 알림)하고 `markFailed` 경합은 무시하고 계속하며, BUY 재캡(`BuyOrderPriceCapper`)은 `cancelPlanned`로 원본을 취소해 경합이면 재캡 트랜잭션 전체를 롤백·생략한다. 개별 취소는 최신 상태로 재판정(PLACED면 증권사 취소), 재주문은 400으로 중단한다. 취소가 SUBMITTING을 만나면 `SubmittingOrderAwaiter`로 최대 60초(KIS 게이트 20초+읽기 7초+401 재시도 ≈ 54초, Toss ≈ 42초) 기다린다(선점 후 60초가 지난 잔류는 결과가 바뀌지 않으므로 기다리지 않는다 — 런북 정정 전까지 매 취소가 묶이지 않게) — PLACED가 되면 증권사 취소, 여전히 SUBMITTING이면 일괄 취소는 재시도 가능한 실패로 집계(삭제·탈퇴 차단 + 관리자 알림), 개별 취소는 "주문 접수를 처리하는 중입니다" 안내. 취소 경로는 재요청 대사를 하지 않는다(취소할 주문을 새로 접수할 수 있어서). 남은 창: 진행 중인 HTTP 1건(선점~응답)은 어떤 설계로도 회수할 수 없어 접수 뒤 취소로만 보정된다(장중 지정가는 그 사이 체결 가능) — 다만 선점 덕에 루프에 남은 주문은 보내지 않는다. 배치 접수 루프와 겹친 일시정지 응답은 최대 1분 걸릴 수 있다. 수동 실행은 거래일이 휴장이면 409로 거부한다.
- **수동 체결 보정(`ManualTradeCorrectionService`)**: 사이클 행 잠금(`lockForUpdate`) 후 (거래일, 증권사 주문번호)가 이미 반영됐거나 요청 안에서 겹치면 400(주문번호 없는 fill은 미검사), DCA는 증권사 잔고 SSOT라 400. 청산 시 사이클 종료·PAUSED는 `endsCycleOnLiquidation()` 전략(INFINITE·PRIVACY)만 — VR은 사이클·상태 유지(닫으면 재개가 VR 사이클을 재오픈하지 않아 좀비로 영구 정지).

### TradingService 기록 테이블 구분
- `orders`: 주문 단위 이벤트 로그 — 실행당 N건 (mainOrders + corrections 모두 저장, order_type/direction/quantity/price/status 포함)
  - `order_leg`: 내부 leg 식별자. 신규 전략 주문은 `INFINITE_EARLY_AVG_BUY`, `VR_BUY_01`, `PRIVACY_SELL_01` 같은 concrete 값을 저장하고, 과거 행은 `UNKNOWN`으로 backfill돼 있고 수동 체결(`filledManual`) 행도 `UNKNOWN`이다. 브로커 API와 외부 응답 DTO에는 전달하지 않는다.
  - 증권사 접수 확정 거절 → `OrderPort.markFailed(orderId)`로 FAILED 기록, 결과 불명은 SUBMITTING 유지 (`OrderSubmitter`)
  - 체결 리포트 집계 시 체결 내역 없는 PLACED 주문(미체결) → `OrderPort.markCancelled(orderId)`로 CANCELLED 기록 (`TradingReporter`). 체결 조회 직전에 `cancelUnresolvedOrders`가 **전 증권사 공통**으로 잔여 PLACED를 증권사에 취소 요청한다(지정가는 애프터장까지 살아 있어, 취소 없이 CANCELLED로 기록하면 이후 체결이 원장에서 누락됨). 이미 종결된 주문(체결·취소·장 마감 만료)은 어댑터가 예외가 아니라 `CancelOutcome`(ALREADY_FILLED/ALREADY_CANCELED)으로 반환하고 리포트는 관리자 알림 없이 넘긴다. 그 외 취소 실패만 `[잔여 주문 취소 실패]` 관리자 알림
- `cycle_position`: 사이클 단위 포지션 스냅샷 — 실행당 1건 append (`CyclePositionPort.save()`, dedup/UNIQUE 제약 없음). 필드: usd_deposit/avg_price/holdings/closing_price
