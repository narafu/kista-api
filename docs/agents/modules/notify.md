## com.kista.notify (`:api`)

com.kista.notify/    ← Spring Modulith 모듈(CLOSED) — Telegram/FCM **순수 아웃바운드 알림 게이트웨이**. 자체 UseCase 없음, 다른 모듈 유스케이스·trading-core HTTP 호출 0(`HexagonalArchitectureTest.notify_must_stay_pure_outbound_gateway`가 `..application.usecase..`·`org.springframework.web.client..` 의존을 잠금). `application.port.output`("port")·`domain.model`("domain") 공개, 나머지 internal. SSE wire 타입은 `com.kista.contract`(`TradeEventMessage`/`TradeEventEnvelope`)를 그대로 쓴다
  domain/model/       ← `NotificationRecipient(userId, nickname, notificationChannel, telegramBotToken, telegramChatId, rejectReason)` + `hasTelegramBot()` — notify가 알림 발송에 실제로 읽는 필드만 담은 notify 소유 투영(trading-core `TradingUserProfile`과 같은 접근). **`User` 애그리게이트를 모른다** — 변환은 gateway 어댑터 경계의 package-private 헬퍼 `NotificationRecipients.from(User)` 1곳이 맡는다(`CompositeUserNotificationAdapter`·`UserChannelNotifier`가 ID로 `UserPort`에서 재조회한 `User`를 변환). `NotificationChannel`은 `com.kista.sharedkernel` 소유(user 설정 저장 + notify 채널 라우팅 공유 어휘)
  application/port/output/ ← NotifyPort/UserNotificationPort(4메서드 — 관리자 신규가입 2 + 승인/거절 2, 모두 `NotificationRecipient`)/FcmDeviceTokenPort — "port". `contract.notify.TradeEventMessage`는 SSE 실시간 매매 알림 wire — trading-core `RedisTradeEventPublisher`(발행)와 root `RedisTradeEventSubscriber` → `TradeSseEmitterRegistry`(구독·kista-ui SSE)가 같은 타입(+ `TradeEventEnvelope`)을 컴파일 타임에 공유한다. `TradeLegSummary`(sharedkernel)와 별개 타입. `SseEmitterRegistry.notifyStatusChange`/`TradeSseEmitterRegistry.connect`·`send`는 포트 없이 구체 클래스로 직접 주입(호출자가 `adapter.in.web` 컨트롤러 2곳뿐이라 포트 역전 불필요)
  adapter/in/web/     ← FcmController/TradeStreamController(매매 이벤트 SSE)/StatusStreamController(`GET /api/auth/status-stream`) + dto/FcmTokenRequest
  adapter/out/gateway/ ← TelegramAdapter(관리자봇 `NotifyPort` — `notifyError`는 발송 전 `AppErrorRaisedEvent`를 발행해 admin 리스너가 `app_error_logs`에 저장하게 한다, trading-core `TradingNotifyAdapter.notifyError`와 동일 구조), CompositeUserNotificationAdapter(가입/승인/거절/재신청 리스너 4종 소유 → TelegramUserNotificationAdapter + FcmAdapter(사용자 알림)), UserChannelNotifier(package-private — **알림 유형 무관 사용자 채널 라우팅 공용 컴포넌트**: `notify(userId, NotificationType, title, body)`가 수신자 조회(없으면 warn 후 skip) → `UserSettings.isNotificationEnabled(type)` 설정 게이트 → 텔레그램 봇(`TelegramHttpClient.sendMessage`, 본문은 호출자가 준 그대로) + `PushNotificationPort.pushIfEnabled` 순으로 발송하고, 채널 leg는 각각 try/catch로 격리해 한쪽 실패가 다른 쪽·호출자로 전파되지 않는다. 발행자 이벤트 리스너는 이벤트 → (유형, 제목, 본문) 매핑만 하고 여기에 위임 — 새 알림 유형의 리스너는 이 컴포넌트를 재사용하고 라우팅 로직을 복제하지 않는다), FinanceReminderChannelNotifier(finance 서비스 `FinanceRegistrationReminderNotifier`와 이름을 구분 — finance가 발행하는 `FinanceRegistrationReminderDueEvent`를 `AlertNotifier`처럼 발행자 이벤트로 동기 `@EventListener` 구독해 `NotificationType.FINANCE_REMINDER`로 `UserChannelNotifier`에 한 줄 위임), UserPushNotificationAdapter(`PushNotificationPort` 구현 — `UserPort.findById` → 없으면 debug 후 skip, `includesFcm()`이면 `FcmAdapter.send`. FCM 라우팅 판정의 단일 지점), NotificationRecipients(package-private `User`→`NotificationRecipient` 변환 헬퍼), TelegramBotInfoAdapter(user `TelegramBotInfoPort` 구현 — `TelegramHttpClient.getBotUsername` 위임), FcmConfig + 이벤트 리스너 4종(UserDeletedNotifier/AlertNotifier(market `FearGreedFetchFailedEvent`·benchmark `BenchmarkAlertRaisedEvent` 구독 — 둘 다 `NotifyPort.notifyError`로 위임)/SchedulerNotifier/UserFcmCleanupListener). `FcmAdapter.send(userId, title, body)`는 package-private — 외부 호출은 `PushNotificationPort`를 거친다. **Telegram HTTP(`TelegramHttpClient`/`TelegramConfig`/`TelegramProperties`)는 `com.kista.platform.telegram`으로 통합**(trading-core `tradingnotify`와 공용) → `docs/agents/modules/platform.md`
  adapter/in/redis/   ← PushNotificationStreamConsumer(trading-core 체결·개장·마감 FCM 푸시 위임 요청 `stream:user.push-notification.requested` 컨슈머 그룹 `root` — platform `RedisStreamSubscriber` 상속, `onRecord`에서 `UserPushNotificationRequestedEvent` 역직렬화 → `PushNotificationPort.pushIfEnabled`(사용자 없음은 조용히 skip). 구독·ack·`cancelOnError=false`·5분 주기 재기동·XCLAIM 복구는 베이스, `@Scheduled` 배선만 서브클래스. Pub/Sub와 달리 root가 잠시 내려가도 기동 후 이어서 소비한다, 보존 상한 `RedisStreamConfig.PUSH_NOTIFICATION_MAXLEN`=10,000건)
  adapter/out/sse/    ← SseEmitterRegistry(사용자별)/TradeSseEmitterRegistry(매매 이벤트) — `sse` 경로 세그먼트 유지 필수(`HexagonalArchitectureTest.sse_emitter_registry_must_not_be_used_in_application_layer`의 `com.kista..adapter.out.sse..` 와일드카드)
  adapter/out/persistence/ ← FcmDeviceTokenEntity + FcmDeviceTokenJpaRepository + FcmDeviceTokenPersistenceAdapter

**남은 `notify → user` 의존(전부 허용 범위)**: user 이벤트 4종 구독(`NewUserRegisteredEvent`/`UserApprovedEvent`/`UserRejectedEvent`/`UserReappliedEvent`) + `UserPort`/`UserSettingsPort`(`CompositeUserNotificationAdapter`·`UserChannelNotifier`·`UserPushNotificationAdapter`의 사용자 조회와 `UserChannelNotifier`의 설정 조회 — `User`/`UserSettings`는 gateway 어댑터 안에서만 import) + `TelegramBotInfoPort` 구현. `notify → admin`은 0건이며 유지해야 한다(`TelegramAdapter.notifyError`가 `AppErrorRaisedEvent`(sharedkernel)를 발행하고 admin `AppErrorRaisedListener`가 구독하는 이벤트 경로라 양방향 모두 결합이 없다). `notify → finance`는 `finance.application.event`("event" NamedInterface)의 `FinanceRegistrationReminderDueEvent` 구독 1건뿐 — market/benchmark 발행자 이벤트를 `AlertNotifier`가 구독하는 선례와 동일하고 `finance → notify`는 0건이라 순환이 없다.

**텔레그램 봇 명령 채널(`/status`·`/history`·승인/거절 콜백)은 notify가 아니라 admin 소유** → `docs/agents/modules/admin.md` `adapter/in/telegram/`. **매매 알림 6종(TradingAlertNotifier/CycleEndedNotifier/CycleLifecycleNotifier/OrderCancelFailureNotifier/TradingReportNotifier/PrivacyAlertNotifier)은 이 모듈이 아니라 `com.kista.tradingnotify`(trading-core) 소유** → `docs/agents/modules/tradingnotify.md` 참고.
