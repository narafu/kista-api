## com.kista.api.web (`:api`)

com.kista.api.web/       ← Spring Modulith 앱셸 모듈. `@ApplicationModule(Type.CLOSED)` — NamedInterface **0개**. 아무 모듈도 web을 참조하지 않는 sink라 순환에 참여할 수 없다(`HexagonalArchitectureTest.web_must_stay_pure_inbound_sink`가 trading-core 대칭 셸 `tradingcore.web`과 함께 `web → ..application.service../..adapter.out..` 의존 금지로 강제). **신규 파일이 단일 모듈만 소비하거나 모듈 의존이 없으면 web에 두지 말고 소유 모듈로 보낼 것** — 여기엔 진짜 다중 모듈 fan-out과 순환 회피용 포트 구현체만
  ApiExceptionReporter  ← `platform.web.ExceptionReporter` 구현 `@Component` — 공용 advice(`platform.web.ProblemDetailExceptionHandler`)가 넘긴 미매핑 500 예외를 `AppErrorRaisedEvent`(sharedkernel, caller=`ApiExceptionReporter`)로 발행한다. 저장은 admin `adapter/in/event/AppErrorRaisedListener`가 담당하므로 web → admin 포트 의존은 없다. 예외→HTTP 매핑 자체는 각 모듈의 `adapter/in/web/*ProblemDetails`(user·admin·market·finance)가 기여한다
  RootSecurityPolicy    ← `platform.security.SecurityRoutePolicy` 구현 `@Component` — root 프로세스 고유 라우트 규칙 11개(`/telegram/webhook`·`POST /api/client-errors`·`/api/auth/**`·`GET /api/market/**`·`GET /api/meta`·`GET /api/runtime-config` permitAll, `/api/auth/status-stream`·`/api/trades/stream`·`DELETE /api/auth/me`·`GET /api/auth/me`·`POST /api/auth/approval-requests` authenticated — principal을 읽는 `/api/auth` 핸들러는 permitAll이면 토큰 없을 때 null로 들어가 500이었다)를 기존과 같은 상대 순서로 기여(구체 경로가 `/api/auth/**` permitAll보다 먼저). `SecurityConfig`가 공통 규칙 뒤에 적용하므로 이 정책이 admin/internal 경로를 permitAll로 열 수 없다. 공개 읽기 4경로(`POST /api/client-errors`·`GET /api/market/**`·`GET /api/meta`·`GET /api/runtime-config`)는 매처 상수로 permitAll 등록과 `anonymousFallbackMatchers()`(무효 토큰 익명 통과)에 공유한다 — `/api/auth/**`는 `/me`·`/approval-requests`가 principal을 읽어 제외. trading-core 셸(`tradingcore.web`)은 대칭 `TradingSecurityPolicy`로 자기 규칙을 기여한다
  UserEventResubmitScheduler ← user 이벤트 Redis 발행 실패분(FAILED `UserDeletedEvent`·`UserNotifyProfileChangedEvent` publication)을 `FailedEventPublications`로 10분마다 재발행하고 첫 실패 발견 회차에 `NotifyPort.notifyError`로 관리자 알림. user에 두면 notify→user 의존과 순환이라 앱셸에 둔다. `@ConditionalOnProperty(scheduler.enabled)` — kista-scheduler(public EPR 재발행 소유)만 (소유 모듈 user는 notify 순환으로 불가, notify는 순수 아웃바운드 게이트웨이, admin은 무관해 앱셸 유지). trading-core `UserEventResubmitScheduler`와 골격(MIN_AGE·BATCH_SIZE·필터)이 같지만 `shared.platform`으로 추출하지 않는다(2곳뿐이라 추출 기준 미달, 필터 이벤트 타입이 `shared.kernel`이라 platform이 참조 불가, 알림 포트·문구가 달라 실제 공통부는 상수 2개뿐).

  AdminSchedulerController ← benchmark "schedule" 소비 — KbLand 스케쥴러 수동 트리거(`/api/admin/scheduler/kbland-*`). 클래스 레벨 `@ConditionalOnProperty(scheduler.enabled)`라 kista-api role에선 빈 미등록(오라우팅 시 404)
  dto/                 ← MetaBundle·EnumMeta·StrategyTypeMeta(`from(StrategyType)` — `StrategyType.capability()`에서 조립)·TickerMeta

### 예외 응답 자동 처리 (공용 advice)
- Controller에서 catch/rethrow 하지 않는다 — advice는 프로세스당 `platform.web.ProblemDetailExceptionHandler` 하나다(`ProblemDetailAutoConfiguration`이 등록, `@WebMvcTest` 슬라이스에도 `AutoConfigureWebMvc.imports`로 올라온다). 다른 `@RestControllerAdvice`를 만들지 않는다 — catch-all을 가진 advice가 둘이면 먼저 평가된 쪽이 모든 예외를 잡는다
- **예외 매핑 SSOT**: 예외를 소유한 모듈의 `adapter/in/web/<Module>ProblemDetails`(`ProblemDetailMappingContributor` 빈)가 `mappings()` 표(`Mapping(status, title, code, fixedDetail)`)로 기여하고, 표로 못 나타내는 응답(헤더·동적 title·오류 보고 — `User.CooldownException` 429+`Retry-After`, `BrokerApiException` 503)만 `responders()`로 기여한다. advice가 `GENERIC`과 합쳐 클래스 계층 탐색(가까운 클래스 우선)으로 찾고, 같은 예외를 두 곳이 기여하면 기동 실패. 기여 인터페이스가 `WebMvcConfigurer`를 확장하는 것은 `@WebMvcTest` 슬라이스에 기여 빈을 올리기 위해서다
- 미매핑 500은 프로세스별 `ExceptionReporter` 빈(root `web.ApiExceptionReporter`·trading-core `tradingcore.web.TradingExceptionReporter`)으로 보고한다. 슬라이스 테스트에는 이 빈이 없어 보고를 건너뛴다 — 보고를 단언하는 슬라이스 테스트는 직접 `@Import`. 현재 응답은 `ExceptionResponseTableTest`(root·trading-core)가 표로 고정한다
  - 범용 예외 타입 선택: 부재=`NoSuchElementException`(404, 고정 문구라 메시지에 진단용 id 허용), 상태=`IllegalStateException`, 입력=`IllegalArgumentException`(둘 다 400, 메시지 원문이 detail). application·domain의 IAE/ISE 리터럴은 "~니다."로 끝나야 한다 — 가드 `ExceptionMessageFormatTest`(기존 위반은 `exception-message-allowlist.txt`에 동결, 고치면 지운다)
- **ProblemDetail 응답 계약**: `detail`은 사용자에게 그대로 보여줄 수 있는 한국어 문구다(완전한 문장은 "~습니다."+마침표). 내부 정보(URL·응답 바디·계좌번호·enum 원문·영어 프레임워크 메시지)는 detail에 싣지 말고 로그로 — 영어 내부 정보인 프레임워크 예외는 `Mapping.fixedDetail`로 고정 문구를 쓴다. 예외: 검증 실패(`MethodArgumentNotValidException`)는 "[field: message]" 형식 유지
- **기계 판독 코드 `code`**: UI가 분기하거나 문구를 달리 보여줘야 하는 예외만 `ErrorCode`(`com.kista.shared.platform.web`)를 `Mapping`에 지정한다. 상수 이름 변경·삭제 금지(kista-ui 계약). 추가 절차: ① `ErrorCode` 상수 ② 소유 모듈 `*ProblemDetails`의 `Mapping(status, title, code, fixedDetail)` ③ 같은 예외 클래스가 여러 의미면 서브클래스 분리(`resolve()`가 계층 하위부터 탐색 — 예: `AlreadyOrderedTodayException`) ④ openapi는 `ErrorCodeOpenApiCustomizer`가 자동 반영 → kista-ui `gen:types` + 문구 매핑
- **내부 API 경유 한계**: root 내부 API 어댑터는 trading-core 응답의 status만 보고 `Admin*` 예외를 되살린다. 같은 status에 서로 다른 코드가 실려 오는 경로가 생기면 `InternalApiErrorDetails`가 `code`도 읽어 전달하도록 확장한다
