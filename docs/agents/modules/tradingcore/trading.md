### TDA 전략 패턴 (InfiniteStrategy)
- **`preview()` today 오프셋**: 날짜 경계는 KST 04:30 (`DstInfo.SCHEDULER_RUN_TIME`) → `TradingPreviewService`의 `today = DstInfo.nextTradeDate(ZonedDateTime.now(clock))` SSOT 사용 (미적용 시 PRIVACY `findTodayTrade()` 날짜 1일 어긋남)
- **`INSUFFICIENT_BALANCE` skip 시 position 포함**: skip이어도 `InfinitePosition`을 `CycleOrderStrategy.OrderPlan`에 보존 — 프론트에서 단위금액·현재가·부족 금액 표시 목적

### VR 전략 패턴 (밸류리밸런싱)
공식·bootstrap 규칙·가격 캡·롤오버 조건의 SSOT는 `docs/agents/modules/tradingcore/trading-formulas.md` "VR 공식" — 여기서는 구조·흐름만 기록.
- **TQQQ 전용** — `StrategyType.VR.capability()`가 ticker를 `TQQQ` 단일로 고정. divisionCount 없음(null 직렬화), cycleSeedType=NONE 강제
- `strategy_vr_version` (`StrategyVrVersionEntity`): 전략 버전별 VR 설정 — intervalWeeks(롤오버 주기), bandWidth(밴드 폭 %), recurringAmount(USD, 양수=적립·0=거치·음수=인출) + 램프 파라미터 8개(initialGradient/gGraceWeeks/gStepWeeks/gMax/initialPoolLimitRate/pGraceWeeks/pStepWeeks/poolLimitFloor)
- `strategy_cycle_vr` (`StrategyCycleVrEntity`): 사이클 시작 시 스냅샷 — value(사이클 기준 V값), gradient(경과주수 기준 `gradientAt()` 재계산값), poolLimitRate(비율 스냅샷, 달러 아님 — poolLimit은 개장 `CyclePosition.usdDeposit×poolLimitRate`로 조회 시점 파생). `StrategyCycle.startAmount`는 개장 예수금+개장 보유분 시장가다(PRIVACY 중간부터 시작은 FIDA 기준 배수 환산 → trading-formulas.md).
- 주문 생성: `CycleOrderComputer` → `VrCycleOrderStrategy.plan()` → `VrStrategy.buildOrders()` → 매수·매도 사다리 LIMIT+AT_OPEN 주문 생성 (bootstrap은 LOC+AT_CLOSE)
- **holdings=0에도 사이클 유지** — `endsCycleOnLiquidation()=false`, `CyclePositionPersistor`가 종료 미발동
- **N주 롤오버**: `VrCycleRolloverService.rollIfDue()` — `CyclePositionPersistor`의 포지션 저장 직후 매일 판정, due이면 V′ 계산 후 기존 사이클 종료 + 새 사이클 원자 생성 (V′≤0 보류 등 규칙 → trading-formulas.md). gradient·poolLimitRate는 스냅샷 이월이 아닌 전략 최초 사이클 startDate 기준 경과주수로 매번 재계산
- **운영 중 재설정**: `VrReconfigureService`(package-private) + `VrReconfigureUseCase` — `PUT /api/trading-cycles/{id}/vr-config`로 밴드폭·주기·적립금·램프 파라미터 수정 + 선택적 투자금 추가/인출을 새 버전 발급+강제 롤오버 1회로 처리(시작예정일 전이면 새 사이클 없이 첫 사이클 in-place 갱신). 상세 규칙 → trading-formulas.md "VR 공식"
- **진행 중 투자금 추가**: `CapitalInjectionService`(package-private) + `InjectCapitalUseCase` — `POST /api/trading-cycles/{id}/capital-injection`(PRIVACY·INFINITE·DCA). DCA는 예수금만 추가(주식 수량 지정 시 400). 금액 자릿수는 계좌 통화 기준(KRW 정수·USD/USDT 소수 2자리). 코인 계좌는 마감 리포트가 없어 리포트 창 검사를 건너뛴다(`CryptoLedgerRecorder`와 사이클 잠금으로 직렬화). 사이클을 유지하고 `lockForUpdate` 후 잠금 뒤 재조회한 사이클의 최신 포지션 행을 in-place 갱신(예수금·주식 가중평균 평단가 — append하면 INFINITE 리버스 판정·별점가·이력이 왜곡, `updateSeed`와 같은 방식), `startAmount`에 추가분 가산(위 비-VR `holdings=0` 갱신 규칙의 예외). 마감 리포트(`TradingService.reportAll`)는 저장 직전 최신 포지션을 재조회해 이런 중간 변경을 덮어쓰지 않는다. 추가·인출은 `CycleCapitalEventPort.save`로 `cycle_capital_event`(trading V15)에 INJECT/WITHDRAW 이력을 같은 트랜잭션에서 남기고(통계가 과거 원금·자산 복원에 사용), 이력이 있는 사이클은 `StrategyService.updateSeed`가 시드 수정을 400으로 거절한다
- **진행 중 투자금 인출**: 같은 `CapitalInjectionService`가 `WithdrawCapitalUseCase`도 구현 — `POST /api/trading-cycles/{id}/capital-withdrawal`(PRIVACY·INFINITE·DCA, body `amount`). 같은 잠금 로직으로 최신 포지션 `usdDeposit`과 `startAmount`를 in-place 차감한다. 인출 가능액 = 장부 예수금 − 오늘·다음 거래일 체결 전(PLANNED/SUBMITTING/PLACED) BUY 약정(`StrategyLedgerBudget.remaining` 재사용) − 아직 마감 리포트 전인 날짜의 접수 후 CANCELLED된 BUY(UNKNOWN_LEG 제외)의 기록된 체결분(`StrategyLedgerBudget.pendingCancelledFill` — 취소 직후 `CancelledOrderFillRecorder`가 기록, 체결량을 모르면 주문 금액 전체. 리포트 끝난 날짜는 장부에 이미 반영돼 제외), 코인 계좌는 체결이 즉시 원장에 반영되므로 날짜 무관 미체결 주문(`findOpenByAccountId`, 같은 사이클)만 약정으로 빼고 취소 보류 체결분은 빼지 않는다. 초과·인출 후 startAmount ≤ 0이면 400. 브로커 호출·강제 매도 없음(다음 주문 계산부터 반영, 넘친 보유분은 매수 축소로 흡수). 추가·인출 모두 오늘 postClose 이후 리포트 마커(`TradingBatchRunPort.isReported`) 전이고 오늘 전략 주문이 있으면(정지 전략은 증권사 접수 주문이 있을 때만 — `CloseReportScope`) 400(마감 리포트가 읽은 잔고로 행을 append해 in-place 변경을 덮어쓰므로 — 리포트 실패 시 다음 날 해제). 관리자 수동 체결 보정(`ManualTradeCorrectionService`)도 같은 창에 400으로 거절한다(코인 계좌 제외, 사이클 잠금 직후). 응답 `ledgerDeposit`(계좌 통화 — 구 `ledgerUsdDeposit`, DB `cycle_position.usd_deposit`·도메인 `usdDeposit`은 이름 유지)이 UI 최대 인출 기준. 초과 오류 문구는 USD면 `$`, 그 외는 `Currency.format`

### Account ↔ Strategy 분리
계좌·전략은 별도 aggregate — 필드 구성은 코드가 SSOT, 아래는 코드로 자명하지 않은 제약·역할만 기록.
- `Account`(account 모듈 소유): type/status/ticker/multiple/updatedAt **없음** (전략 속성은 Strategy로 분리). `updatedAt`은 persistence `BaseAuditEntity`가 관리, `createdAt`은 신규 등록 시 null → persistence 저장 후 채워짐
- `Strategy`: `StrategyType`/`StrategyStatus`/`StrategyTicker`/`StrategyCycleSeedType`는 `com.kista.shared.kernel`의 전역 공용 어휘 — nested 재도입 금지, DB `@Enumerated(STRING)` 컬럼 상수명 byte-identical 유지. `Strategy` record 자체는 `com.kista.tradingcore.trading.domain.model`에 위치
- 설정 이력 계층: `StrategyVersion`(버전 부모) → `StrategyInfiniteDetail`(divisionCount) / `StrategyVrDetail`(intervalWeeks·bandWidth·recurringAmount + 램프 8필드; `gradientAt(weeks)`/`poolLimitRateAt(weeks)`는 VR 공식 메서드 — `com.kista.tradingcore.matching.domain.model` 소유, "kernel" 공개). `StrategyVersion`/`StrategyInfiniteDetail`은 `com.kista.tradingcore.trading.domain.model`("domain" 공개)
- 실행 이력 계층: `StrategyCycle`(실행된 사이클 + 적용 버전 고정값; `startAmount` 계약 → trading-formulas.md "VR 공식"의 "개장 금액 계약")은 비-VR 최신 포지션 `holdings=0`일 때만 `StrategyCyclePort.updateStartAmount()`로 in-place 갱신. VR 일반 시드 수정은 저장 전에 거부하고 VR 재설정을 사용한다. VR의 개장 USD pool은 개장 `CyclePosition.usdDeposit`(`initialUsdDeposit`)으로 별도 보존 → `CyclePosition`(체결마다 append되는 포지션 스냅샷, dedup/UNIQUE 없음) + 타입별 detail `CyclePositionInfiniteDetail`(isReverseMode) / `StrategyCycleVrDetail`(사이클 시작 VR 파라미터 스냅샷 value·gradient·poolLimitRate)
- `StrategyDetail`: 최신 사이클·활성 버전·최신 포지션을 합쳐 만드는 응답 조립 DTO(`StrategyDetailAssembler.toDetail()`), `vr` 필드는 top-level `com.kista.tradingcore.trading.domain.model.VrSummary`(VR 외 null). **조립 SSOT는 `StrategyDetailAssembler` 하나** — 조회(`StrategyService`)·등록(`StrategyCreationService`, 이미 조회한 계좌 market 사용) 공용이며 등록 전용 조립 분기는 금지다(kista-ui가 POST 응답을 캐시하므로 GET과 값이 어긋나면 안 됨)
- `VrRampValidator.validateWithdrawalSufficiency`는 등록·재설정 공용 단일 규칙이다. 호출이 둘인 이유: 등록은 override V(gate)와 시장가 평가금(required)을 분리해 넘기고, 재설정은 현재가 조회 뒤에만 자산을 알 수 있어 램프 검증(가격 조회 전)과 시점이 다르다 — 한 호출로 합치면 램프 오류에도 브로커 호출이 생긴다.
- 계좌당 종목(ticker) 중복 등록 불가 — `StrategyPort.findByAccountIdAndTicker` (계좌당 여러 전략, 종목별 1개 — DCA 포함 전 전략 공통, 중복이면 409 "같은 계좌에 이미 해당 종목 전략이 있습니다.". 한 종목의 매수·매도는 DCA 한 전략의 규칙으로 표현)
- `cycleSeedType`: 사이클 종료 후 자동 재등록 정책 (기본 `NONE`); **VR은 NONE 강제** — 롤오버가 사이클 교체 담당

### 전략 보관 (ARCHIVED)
- 보관은 ACTIVE·PAUSED → ARCHIVED 한 방향이다(해제 API·메서드 없음). `StrategyService.archive`(NOT_SUPPORTED — 증권사 취소 HTTP 포함)가 보유 0·당일 접수 주문 마감 반영·미체결 취소 성공을 확인한 뒤 `StrategyStateWriter.archive`로 저장한다. 실패 시 PAUSED로 남는다
- 보관 전략 변경 거부: `Strategy.requireNotArchived()`를 pause·resume·update·VR 재설정(`VrReconfigureService`)·DCA 설정(`DcaConfigService`)·투자금 추가·인출(`CapitalInjectionService`)·수동 체결 보정(`ManualTradeCorrectionService`)·상태 API(`StrategyStatusInternalController`, ARCHIVED 요청과 보관 전략 ACTIVE 요청 400)에서 호출한다. 삭제는 보관 전략도 허용한다(소프트 삭제, 통계에서 빠짐)
- 목록·미리보기 제외는 호출부 필터(`!isArchived()`, `includeArchived`)로 한다. `StrategyPort.findByAccountIds`·`findByAccountId`는 보관 포함 그대로 둔다 — 통계(`TradingStatsService`)가 공유하므로 포트에 필터를 넣으면 보관 전략 성과가 사라진다. 계좌당 종목 중복 검사만 보관을 제외한다(`StrategyCreationService`)
- 상태 쓰기 경합: 보관은 되돌릴 수 없으므로 오래된 스냅샷 `save(withStatus(...))`로 PAUSED/ACTIVE를 쓰지 않고 `StrategyPort.updateStatusUnlessArchived`(조건부 UPDATE, 0건이면 false)를 쓴다 — `resume`·`pause`(0건이면 "보관된 전략은 변경할 수 없습니다.")·`StrategyStateWriter.pause`·`StrategyPort.pause` default. 보관 확정은 `StrategyPort.archiveIfPaused`(PAUSED일 때만, 0건이면 "전략 상태가 바뀌어 보관하지 못했습니다." — 재개와의 경합). 삭제는 `pause` 결과를 무시해 보관 전략도 삭제된다. 어댑터의 두 조건부 갱신은 `@Transactional` 필수(스케쥴러 경로엔 바깥 트랜잭션이 없다). 예외: `CycleCloser`(수동 보정 — `requireNotArchived`가 먼저 거부)
- 마감 리포트 백스톱: `findNotActiveWithReportableOrders`가 PAUSED뿐 아니라 ARCHIVED도 잡아 보관 직전 접수분 체결을 원장에 남긴다. 리포트 경로는 `!isActive()`로 정지와 같이 취급돼 사이클 종료만 기록하고 rotation·알림·VR 롤오버·상태 쓰기는 없다
- 신규 상태를 추가하면 `status != PAUSED`가 아니라 `isActive()`로 판정한다 — 배치·정산·리포트 판정이 ARCHIVED를 매매 대상으로 잘못 잡지 않게 한다

### 전략 원장 상한 (상세 규칙 SSOT → workflow-ledger-price.md)
- 원장 상한 판정·compute skip·실패 격리 등 실행 규칙 전체는 `docs/agents/workflow-ledger-price.md` "스케쥴러 실행 흐름"이 SSOT — 매매·스케쥴러·주문 로직 작업 시 workflow.md 인덱스 참고
- `orders.order_leg`는 스케쥴러 내부 leg 식별자 — 신규 전략 주문은 non-blank concrete leg 필수(`UNKNOWN` 잔존 시 배치는 `TradingCandidatePlanner.validateConcreteOrderLegs`가 원장 판정·슬롯 필터 전에 전략 타입과 함께 `IllegalStateException`으로 거절하고, 공용 저장 지점 `TradingOrderPlanner.savePlannedOrders`도 수동 실행·재캡 포함 모든 저장을 거절 — 앞단 검사를 지우면 결함이 원장 부족 알림·슬롯 중복 제외로 가려지므로 둘 다 유지), 과거 행·수동 체결 행은 `UNKNOWN` 유지, 브로커 API payload에 미포함
- 슬롯 점유 판단: `timing + direction + orderLeg`(UNKNOWN coarse 처리는 제거됨)
- `orders.order_leg`와 scheduler/reservation 조회용 인덱스(`idx_orders_cycle_date_timing_status` 등)는 trading baseline(`db/migration-trading`)에 포함돼 있다 — 후속 orders 쿼리 변경 시 인덱스 prefix와 조회 조건 함께 확인

### 런타임 매매 정책 적용 (TradingPolicyService)
정책 값은 `trading.trading_runtime_settings`(`TradingPolicyService`가 소유)에 있고, root admin `GET|PUT /api/admin/settings`가 내부 API로 조회·교체한다(엔드포인트 규칙 → `modules/api/admin.md` "런타임 설정 API 규칙").
- `brokers.<broker>.enabled=false`이면 해당 증권사의 신규 계좌 등록과 연결 테스트를 외부 API 호출 전에 400으로 차단. 기존 계좌의 조회·수정·매매는 영향받지 않음
- `StrategyService.register()`(정책 조회는 `StrategyCreationService`가 `StrategyCreationPolicyPort`로)는 신규 전략에만 `strategies.<type>` 생성 정책을 적용: `enabled=false`면 400으로 차단하고, ticker·INFINITE divisionCount·VR recurringMode/bandWidth/intervalWeeks의 생략 기본값과 허용/고정값을 검증. 기존 전략 수정·실행에는 소급 적용하지 않음
- `RegisterStrategyCommand.divisionCount=null`은 INFINITE 신규 등록의 미입력이며 `InfiniteCreationResolver`가 런타임 기본값으로 치환한다(명시적 0은 허용값이 아니라 400). VR `recurringAmount` 생략도 null로 넘어가 `VrCreationResolver`가 정책 기본 `recurringMode`로 정한다(HOLD면 0, 그 외는 400). VR `recurringMode`는 `recurringAmount` 부호(DEPOSIT/HOLD/WITHDRAW)로만 검증하고 금액 크기는 기존 VR 자산 규칙에 맡김. `recurringMode.customizable=false` 설정은 기본값과 유일한 허용값이 모두 `HOLD`여야 함
