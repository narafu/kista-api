### TDA 전략 패턴 (InfiniteStrategy)
- **`preview()` today 오프셋**: 날짜 경계는 KST 04:30 (`DstInfo.SCHEDULER_RUN_TIME`) → `TradingPreviewService`의 `today = DstInfo.nextTradeDate()` SSOT 사용 (미적용 시 PRIVACY `findTodayTrade()` 날짜 1일 어긋남)
- **`INSUFFICIENT_BALANCE` skip 시 position 포함**: skip이어도 `InfinitePosition`을 `CycleOrderStrategy.OrderPlan`에 보존 — 프론트에서 단위금액·현재가·부족 금액 표시 목적

### VR 전략 패턴 (밸류리밸런싱)
공식·bootstrap 규칙·가격 캡·롤오버 조건의 SSOT는 `docs/agents/modules/tradingcore/trading-formulas.md` "VR 공식" — 여기서는 구조·흐름만 기록.
- **TQQQ 전용** — `StrategyType.VR.capability()`가 ticker를 `TQQQ` 단일로 고정. divisionCount 없음(null 직렬화), cycleSeedType=NONE 강제
- `strategy_vr_version` (`StrategyVrVersionEntity`): 전략 버전별 VR 설정 — intervalWeeks(롤오버 주기), bandWidth(밴드 폭 %), recurringAmount(USD, 양수=적립·0=거치·음수=인출) + 램프 파라미터 8개(initialGradient/gGraceWeeks/gStepWeeks/gMax/initialPoolLimitRate/pGraceWeeks/pStepWeeks/poolLimitFloor)
- `strategy_cycle_vr` (`StrategyCycleVrEntity`): 사이클 시작 시 스냅샷 — value(사이클 기준 V값), gradient(경과주수 기준 `gradientAt()` 재계산값), poolLimitRate(비율 스냅샷, 달러 아님 — poolLimit은 개장 `CyclePosition.usdDeposit×poolLimitRate`로 조회 시점 파생). `StrategyCycle.startAmount`는 개장 예수금+개장 보유분 시장가다(PRIVACY 중간부터 시작은 FIDA 기준 배수 환산 → trading-formulas.md).
- 주문 생성: `CycleOrderComputer` → `VrCycleOrderStrategy.plan()` → `VrStrategy.buildOrders()` → 매수·매도 사다리 LIMIT+AT_OPEN 주문 생성 (bootstrap은 LOC+AT_CLOSE)
- **holdings=0에도 사이클 유지** — `endsCycleOnLiquidation()=false`, `CyclePositionPersistor`가 종료 미발동
- **N주 롤오버**: `VrCycleRolloverService.rollIfDue()` — `CyclePositionPersistor`의 포지션 저장 직후 매일 판정, due이면 V′ 계산 후 기존 사이클 종료 + 새 사이클 원자 생성 (V′≤0 보류 등 규칙 → trading-formulas.md). gradient·poolLimitRate는 스냅샷 이월이 아닌 전략 최초 사이클 startDate 기준 경과주수로 매번 재계산
- **운영 중 재설정**: `VrReconfigureService`(package-private) + `VrReconfigureUseCase` — `PUT /api/trading-cycles/{id}/vr-config`로 밴드폭·주기·적립금·램프 파라미터 수정 + 선택적 자본 주입/인출을 새 버전 발급+강제 롤오버 1회로 처리. 상세 규칙 → trading-formulas.md "VR 공식"

### Account ↔ Strategy 분리
계좌·전략은 별도 aggregate — 필드 구성은 코드가 SSOT, 아래는 코드로 자명하지 않은 제약·역할만 기록.
- `Account`(account 모듈 소유): type/status/ticker/multiple/updatedAt **없음** (전략 속성은 Strategy로 분리). `updatedAt`은 persistence `BaseAuditEntity`가 관리, `createdAt`은 신규 등록 시 null → persistence 저장 후 채워짐
- `Strategy`: `StrategyType`/`StrategyStatus`/`StrategyTicker`/`StrategyCycleSeedType`는 `com.kista.shared.kernel`의 전역 공용 어휘 — nested 재도입 금지, DB `@Enumerated(STRING)` 컬럼 상수명 byte-identical 유지. `Strategy` record 자체는 `com.kista.tradingcore.trading.domain.model`에 위치
- 설정 이력 계층: `StrategyVersion`(버전 부모) → `StrategyInfiniteDetail`(divisionCount) / `StrategyVrDetail`(intervalWeeks·bandWidth·recurringAmount + 램프 8필드; `gradientAt(weeks)`/`poolLimitRateAt(weeks)`는 VR 공식 메서드 — `com.kista.tradingcore.matching.domain.model` 소유, "kernel" 공개). `StrategyVersion`/`StrategyInfiniteDetail`은 `com.kista.tradingcore.trading.domain.model`("domain" 공개)
- 실행 이력 계층: `StrategyCycle`(실행된 사이클 + 적용 버전 고정값; `startAmount` 계약 → trading-formulas.md "VR 공식"의 "개장 금액 계약")은 비-VR 최신 포지션 `holdings=0`일 때만 `StrategyCyclePort.updateStartAmount()`로 in-place 갱신. VR 일반 시드 수정은 저장 전에 거부하고 VR 재설정을 사용한다. VR의 개장 USD pool은 개장 `CyclePosition.usdDeposit`(`initialUsdDeposit`)으로 별도 보존 → `CyclePosition`(체결마다 append되는 포지션 스냅샷, dedup/UNIQUE 없음) + 타입별 detail `CyclePositionInfiniteDetail`(isReverseMode) / `StrategyCycleVrDetail`(사이클 시작 VR 파라미터 스냅샷 value·gradient·poolLimitRate)
- `StrategyDetail`: 최신 사이클·활성 버전·최신 포지션을 합쳐 만드는 응답 조립 DTO(`StrategyService.toDetail()`), `vr` 필드는 top-level `com.kista.tradingcore.trading.domain.model.VrSummary`(VR 외 null)
- 계좌당 종목(ticker) 중복 등록 불가 — `StrategyPort.findByAccountIdAndTicker` (계좌당 여러 전략, 종목별 1개 — DCA 포함 전 전략 공통, 중복이면 409 "같은 계좌에 이미 해당 종목 전략이 있습니다.". 한 종목의 매수·매도는 DCA 한 전략의 규칙으로 표현)
- `cycleSeedType`: 사이클 종료 후 자동 재등록 정책 (기본 `NONE`); **VR은 NONE 강제** — 롤오버가 사이클 교체 담당

### 전략 원장 상한 (상세 규칙 SSOT → workflow.md)
- 원장 상한 판정·compute skip·실패 격리 등 실행 규칙 전체는 `docs/agents/workflow.md` "스케쥴러 실행 흐름"이 SSOT — 매매·스케쥴러·주문 로직 작업 시 필수 Read
- `orders.order_leg`는 스케쥴러 내부 leg 식별자 — 신규 전략 주문은 non-blank concrete leg 필수(`UNKNOWN` 잔존 시 배치는 `TradingCandidatePlanner.validateConcreteOrderLegs`가 원장 판정·슬롯 필터 전에 전략 타입과 함께 `IllegalStateException`으로 거절하고, 공용 저장 지점 `TradingOrderPlanner.savePlannedOrders`도 수동 실행·재캡 포함 모든 저장을 거절 — 앞단 검사를 지우면 결함이 원장 부족 알림·슬롯 중복 제외로 가려지므로 둘 다 유지), 과거 행·수동 체결 행은 `UNKNOWN` 유지(재주문 불가), 브로커 API payload에 미포함
- 슬롯 점유 판단: `timing + direction + orderLeg`(UNKNOWN coarse 처리는 제거됨)
- `orders.order_leg`와 scheduler/reservation 조회용 인덱스(`idx_orders_cycle_date_timing_status` 등)는 trading baseline(`db/migration-trading`)에 포함돼 있다 — 후속 orders 쿼리 변경 시 인덱스 prefix와 조회 조건 함께 확인

### 런타임 매매 정책 적용 (TradingPolicyService)
정책 값은 `trading.trading_runtime_settings`(`TradingPolicyService`가 소유)에 있고, root admin `GET|PUT /api/admin/settings`가 내부 API로 조회·교체한다(엔드포인트 규칙 → `modules/api/admin.md` "런타임 설정 API 규칙").
- `brokers.<broker>.enabled=false`이면 해당 증권사의 신규 계좌 등록과 연결 테스트를 외부 API 호출 전에 400으로 차단. 기존 계좌의 조회·수정·매매는 영향받지 않음
- `StrategyService.register()`(정책 조회는 `StrategyCreationService`가 `StrategyCreationPolicyPort`로)는 신규 전략에만 `strategies.<type>` 생성 정책을 적용: `enabled=false`면 400으로 차단하고, ticker·INFINITE divisionCount·VR recurringMode/bandWidth/intervalWeeks의 생략 기본값과 허용/고정값을 검증. 기존 전략 수정·실행에는 소급 적용하지 않음
- `RegisterStrategyCommand.divisionCount=0`은 INFINITE 신규 등록의 미입력 sentinel이며 런타임 기본값으로 치환. VR `recurringMode`는 `recurringAmount` 부호(DEPOSIT/HOLD/WITHDRAW)로만 검증하고 금액 크기는 기존 VR 자산 규칙에 맡김. `recurringMode.customizable=false` 설정은 기본값과 유일한 허용값이 모두 `HOLD`여야 함

### DCA 회차 실행 (다중 규칙)
- 구조: DCA 전략 1개 = 규칙 1~10개(`DcaStrategyConfig.rules`, 규칙마다 방향·주기·주문유형·규모(`DcaSizing` AMOUNT|HOLDING_PERCENT)·부족 정책(`DcaShortfallPolicy` PARTIAL|REJECT)·조건 목록). 저장은 `trading.strategy_dca_rule` + `strategy_dca_condition`(V12, 구 `strategy_dca_version` 대체·sort_order로 입력 순서 보존). 주문 leg는 `"DCA_" + ruleKey`(ruleKey = 서버가 발급하는 UUID 문자열). 같은 날·같은 시점에 발동한 규칙은 각자 주문한다.
- `DcaPlanInputCollector`(마감·개장 배치, 구 `DcaRoundPlanner` 대체): 규칙별 기존 주문 복구 → timing·실행일·이력(UNIQUE 전략+규칙+거래일) 판정 → 250봉 종가 조회(`CandlePort.getDailyCandlesBefore`) → `DcaRuleInputs` 조립. 판정·주문 생성은 주식 경로도 공통 `CycleOrderStrategy.plan`(`DcaCycleOrderStrategy`)이 `decideRule`로 수행한다. 매수 기준가는 max(전일 종가, `TradingCandidatePlanner`가 넘기는 배치 시작 시점 현재가)이고 수량·캡 지정가·`reference_price`가 이 값을 쓴다. 조건 평가는 전일 종가. 마지막 봉 날짜가 직전 US 개장일이 아니면 `DATA_UNAVAILABLE`이며 검증을 통과한 종가는 (티커, US 세션) 단위로 메모리 캐시한다(지난 세션 제거·실패 미캐시). CNN 공포탐욕지수(`FearGreedIndexPort`)는 FEAR_GREED 조건이 있을 때만 10분 TTL 메모로 조회한다. 브로커 실잔고는 SELL 판정에 쓰지 않는다 — 주식 매도 가용 = 원장 보유 − 같은 사이클·거래일 기존 PLANNED/PLACED SELL 예약분 − 같은 배치 앞 규칙 계획 SELL(INFINITE·VR과 같은 원장 기준 — 증권사 거절은 SELL 거절 사용자 알림·프리뷰 `accountHoldingsCheck`가 신호). 코인은 `CryptoDcaRoundExecutor`가 지갑 보유로 추가 상한을 건다. 주식 **BUY**는 원장(시드 없음)이 없어 예외로 브로커 매수가능금액을 읽는다(코인 BUY와 같은 부족 정책 PARTIAL|REJECT 복원): 가용 USD = `UnassignedUsdCalculator.available`(`MarginPort.getUsdBuyableAmount` − 같은 계좌의 시드 점유 전략(`occupiesSeed()`, DCA 제외) 최신 `usd_deposit` 합) − 이 전략 당일 기존 BUY 중 증권사가 아직 차감하지 않은 PLANNED·SUBMITTING(수량 × 가격; PLACED는 이미 차감) — BUY 규칙이 처음 필요할 때 전략당 1회 조회(배치·미리보기·수동 실행 공통 경로, 미리보기는 계좌 `accountCashCheck`와 별도로 1회 더 호출). MOCK·US 주식 외 계좌는 상한 없음, 조회 실패·null은 `DATA_UNAVAILABLE` skip. 다른 전략의 PLACED 주문은 브로커 매수가능금액과 원장 양쪽에서 빠져 이중 차감되는 보수적 편향이 있다(등록 폼 가용 예수금 경고와 같은 계산).
- skip이면 `DcaExecutionRecorder`가 규칙 단위 이력(`dca_execution` UNIQUE(strategy, rule_key, trade_date), `ruleKey`·`direction` 저장)을 쓰고 `DcaRoundSkippedEvent`를 발행한다(→ `TradingAlertNotifier`가 방향·규칙 순번 포함 알림, 삽입 성공 시에만 발행). 증권사 잔고·수량 부족 거절은 `TradingOrderExecutor.reportInsufficient`가 규칙(leg) 단위로 `INSUFFICIENT_BALANCE`(BUY)/`INSUFFICIENT_HOLDINGS`(SELL) 이력을 남긴다.
- API: 등록·수정 본문 `dca.rules[]`(`DcaConfigRequest`/`DcaRuleRequest`/`DcaSizingRequest`) — 구 단일 규칙 필드는 제거(호환 없음). 등록 시 ruleKey를 보내면 400, 수정 시 기존 키 재전송 = 유지(같은 날 재발동 방지)·생략 = 신규·현재 버전에 없는 키 = 400, 응답 rules[]는 입력 순서 보존(`DcaRuleResponse` — 규칙별 `nextExecution`·`lastExecution` 포함). 조회 `dca.currentHoldings`·`dca.avgPrice`는 원장 값(BigDecimal, 코인 소수 포함, 원장 없으면 null)이다. 메타 `strategyTypes[DCA].conditionIndicators`는 `[AVG_PRICE, SMA, RSI, FEAR_GREED]`, `/api/meta`에 `DcaSizingType`·`DcaShortfallPolicy` 라벨이 있다.
- 이력 조회 `GET /api/trading-cycles/{id}/dca-executions`(`DcaExecutionQueryService`)의 `DcaExecutionItem`은 `ruleKey`·`direction`(항상 채움)을 싣는다. 등록·설정은 `DcaConfigService`·`StrategyCreationService`.
- 시장 규칙: `DcaRule.requireCompatible(market)`/`DcaStrategyConfig.requireCompatible`이 SSOT — 코인: MARKET만·`executionHour` 0~23 필수·금액 자릿수·최소 금액은 시장 capability(`Market.amountScale()`/`minOrderAmount()` — KRW 정수·5,000원, USDT 소수 2자리·5)·주말 허용 / 주식: MOO|MOC만·평일만·`executionHour` 무시(NULL). `HOLDING_PERCENT`는 SELL 전용(0 < percent ≤ 100). 계좌 시장 ≠ 종목 시장이면 거부, 코인 계좌는 DCA만. 런타임 정책(기본 비활성)이 켜져 있어야 등록된다.
- 중간부터 시작: DCA도 `initialHoldings`·`initialAvgPrice`를 받는다(주식 정수·코인 소수 8자리). 시작 원가는 사이클 `start_amount`로 기록돼 통계 원금의 기초가 된다(→ stats.md).
- 주식 개장·마감 배치(`BatchContextFactory`)는 US_STOCK 계좌 전략만 담는다 — 코인 DCA 전략은 조용히 제외(묶음 C 전용 스케줄러가 실행). 미리보기(`TradingPreviewService`)는 주식 DCA를 `plan()` 정규 경로로 포함하고(코인 DCA는 `DcaManualExecutionUnsupportedException`), 수동 실행(`ManualTradingService`)은 DCA를 거부한다. DCA 프리뷰는 쓰기를 하지 않고, 당일 이미 판정(이력)·주문된 규칙은 `orders` 후보에서 빼고 `todayOrders`로만 노출한다(같은 규칙을 같은 날 두 번 판정하지 않기 위함). 코인 전략이 브로커 라우터에 닿지 않는다.
- 보유·평단 SSOT는 내부 원장(`cycle_position`) — 다른 전략과 같이 마감 리포트가 자기 주문 체결만 `applyExecutions`로 반영하고, 시드를 점유하지 않아(`occupiesSeed()=false`) usd_deposit은 0이다. 가용 부족(BUY)·보유 없음(SELL)은 규칙(leg) 단위로 `INSUFFICIENT_BALANCE`/`NO_HOLDINGS` 이력을 남긴다.  관리자 수동 보정도 DCA에 열려 있다(주식 정수·코인 소수 8자리 수량). 통계·포트폴리오는 DCA를 포함한다(→ stats.md).
- 개장 배치는 22:00 KST. KIS DCA MOO는 개장 전 접수(`TradingService.placePreOpenDcaOrders`, `Broker.supportsOpenAuctionOrders()` 필터), 접수 후 체크포인트를 STARTED로 되돌리고 이 단계 실패는 격리한다.
- 주문 수량: orders.quantity/filled_quantity·dca_execution.quantity는 numeric(20,8), Order/DcaExecution은 BigDecimal(compact 생성자에서 Quantities.normalize — 꼬리 0 제거). PlannedOrder·매칭 공식·privacy 표는 int이고 주식 경로(브로커 wire·커널 재입력)는 intValueExact()로 변환한다. 재주문(ReorderService)과 일별 체결 요약(AccountStatisticsService)은 주식 주문만 다룬다.
- 원장 holdings: `CyclePosition.holdings`·`CyclePositionHistoryEntry.holdings`는 BigDecimal(normalize), DB `trading.cycle_position.holdings` numeric(20,8)(trading-core 마이그레이션 파일 V11). wire `PortfolioCurrentResponse.holdings`·`TradeCorrectionResponse.finalHoldings`도 BigDecimal(정수는 JSON `5`). `StrategyDetail.currentHoldings`는 Integer 유지(CRYPTO_KRW DCA는 null — 크립토에 `wholeShares()` 호출 금지). 주식 공식 경로는 `AccountBalance.wholeShares()`(소수면 ArithmeticException)로 정수화한다.
- 자기 주문 체결 원칙(`TradingReporter`, 전 전략): 원장(cycle_position)·리포트 leg는 `externalOrderId`가 우리 주문에 속한 체결만 쓴다 = mainOrders(접수 주문 + 당일 사이클/거래일 PLACED) ∪ 같은 사이클·거래일의 CANCELLED 주문(취소·재주문 전 부분 체결). `ManualTradeCorrectionService`의 filledManual FILLED 행은 cycle_position을 직접 쓰므로 제외, `externalOrderId`가 null인 체결은 우리 것이 아니다. 사용자가 앱에서 직접 낸 외부 체결은 수동 정정으로만 원장에 반영된다. CANCELLED 자기 주문에 매칭된 체결은 상태를 CANCELLED로 둔 채 `filled_quantity`/`filled_price`만 기록한다(상태를 바꾸면 리포트 재개 때 `findCancelledByCycleAndDate`에서 빠져 원장이 체결을 잃는다). 체결 금액 집계(`sumFilledBuyAmountByCycleId`·`findFilledNetInvestedByCycleIds`·`findFilledBy*`)는 status가 아니라 `filled_quantity > 0`으로 판정한다 — 취소 경로(`ReorderService`·`OrderCancelService`)는 체결을 기록하지 않으며, 리포트가 돌지 않는 취소(전략 삭제·일시정지)는 원장에도 반영되지 않아 일관된다.

### 코인 DCA 실행 (업비트·바이낸스, 묶음 C)
- 진입: `CryptoDcaScheduler`(`trading/adapter/in/schedule`, cron `0 */10 * * * *` KST, 락 `crypto-dca` 9분, `scheduler.enabled`) → `CryptoDcaExecutionUseCase.runTick(nowKst)` → `CryptoDcaRunner`. 대상은 코인 거래소(업비트 CRYPTO_KRW·바이낸스 CRYPTO_USDT) 계좌의 ACTIVE DCA 전략이고, 계좌별로 `CryptoOrderSynchronizer.sync`(기존 주문 상태 동기화) 뒤 `CryptoDcaRoundExecutor.executeAccount`(회차 판정·주문)를 실행한다. 관리자 오류 알림은 대상별 KST 하루 1회로 중복 제거한다(`reportOncePerDay`). 주식 마감·개장 배치(`BatchContextFactory`)는 코인 계좌 전략을 제외한다.
- 주문 상태: PLANNED → SUBMITTING → PLACED → FILLED/FAILED/CANCELLED. clientOrderId = 주문 UUID(재시도 멱등, 거래소별 고유 범위 상이). **바이낸스는 clientOrderId가 열린 주문 중에서만 고유하고 체결 후 재사용이 허용돼 재전송이 곧 이중 매수다** — 접수는 재전송하지 않고(결과 불명이면 SUBMITTING 유지·다음 틱 조회), 조회의 "없음"은 -2013(과 -2026)만 `Optional.empty()`이며 5xx·-1006·-1007·I/O는 예외다. 바이낸스 체결 시 원장은 받은 자산 수수료를 뺀 순수량(`netExecutedVolume`) 기준이다(→ binance-api.md). 체결 판정은 state와 무관하게 `executedVolume > 0`. 일시 오류는 실행 시(hour) 안에서 재시도하고 분 ≥ 50이면 EXCHANGE_API_ERROR로 확정한다. KEY_EXPIRED 응답은 API_KEY_EXPIRED로 기록한다.
- 수량·금액: 매수 = min(설정 금액, `CryptoTradingRules.affordableAmount`(지갑, 시장 금액 자릿수)) — 수수료·차감 쪽·최소 주문 금액·수량 단위는 `CryptoExchangePort.getTradingRules`(업비트: 0.05% 원화 가산·5,000원·1e-8, 바이낸스: 받은 자산 차감이라 수수료율 미사용·NOTIONAL 최소 금액·LOT_SIZE 수량 단위), 등록 시 최소 금액은 `Market.minOrderAmount()`. 같은 틱은 SELL 규칙을 먼저, BUY를 나중에 처리하며 지갑에 매도 대금을 더하지 않는다. 매도 수량은 거래소 수량 단위(업비트 소수 8자리, 바이낸스 LOT_SIZE stepSize)로 FLOOR 후 min(원장 보유 − 같은 틱 앞 규칙 매도분, 거래소 매도 가능 수량) 이하. 일봉은 250봉(업비트 `to` 페이징), 신선도는 오늘−1일(KST 09시 이후) / 오늘−2일(그 전) 최신 봉.
- 조건 판정은 `matching.DcaConditions.check`를 주식·코인이 `DcaCycleOrderStrategy.decideRule`로 공유한다. FEAR_GREED는 코인 전용 `CryptoFearGreedIndexPort`(`trading/application/port/output`) + `CryptoFearGreedIndexAdapter`(`trading/adapter/out/feargreed`, alternative.me, 실패 시 empty)가 공급한다 — 주식 CNN `FearGreedIndexPort`에 market 인자를 넣지 않고 포트를 분리했다.
- 체결 확정 시(`CryptoOrderSynchronizer`) `CryptoLedgerRecorder#recordFill`이 같은 트랜잭션에서 사이클 원장(cycle_position, 보유·평단)에 반영하고(`usd_deposit` 0) `CryptoOrderFilledEvent`를 발행 → `tradingcore.notify.CryptoTradeNotifier`(→ notify.md). `DcaSummaryAssembler` 코인 분기는 24/7이라 다음 실행을 KST 기준 다음 실행 시각(executionHour)으로 계산한다.
- `OrderCancelService`: 코인 계좌는 PLANNED 주문만 삭제하고, SUBMITTING/PLACED(거래소 전송 중·접수)가 있으면 일시정지·전략 삭제·계좌 삭제를 409 `ORDER_NOT_CANCELLABLE`로 거부한다.
