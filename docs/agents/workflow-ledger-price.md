# 전략 원장 상한·시세·브로커 토큰

배치 실행 순서는 workflow-batch.md("스케쥴러 실행 흐름").

## 스케쥴러 실행 흐름 — 원장 상한·시세·토큰
- 전략별 원장 상한: 각 전략은 자기 원장(`cycle_position.deposit`) 안에서만 BUY를 낸다 — `StrategyLedgerBudget`(`remaining`/`fit` — 전 전략 적용)이 배치·수동 실행·접수 직전 재캡의 공용 판정이다. `remaining(cycle, tradeDate)` = 최신 원장(첫 거래일처럼 `cycle_position`이 없으면 `StrategyCycle.startAmount()`) − 같은 날 이미 저장된 BUY(PLANNED·SUBMITTING·PLACED) 금액과 마감 리포트 전 CANCELLED BUY의 기록된 체결분(`unreportedCancelledBuys`·`pendingCancelledFill` — 체결량을 모르면(`filledQuantity` null) 주문 금액 전체)을 한 번만 차감한 값이다(신규 후보는 `TradingOrderSlots.excludeExisting`으로 이미 저장된 슬롯을 뺀 뒤 판정해 이중 차감이 없다). `fit`은 BUY 총액이 한도를 넘으면 `fitBuysToBudget`으로 1회 축소하고(INFINITE=보정 생략, VR=싼 단부터 절단, PRIVACY=축소 없음) 그래도 못 담으면 BUY 전체를 제거하며 SELL은 항상 유지한다(후보 내부 원래 순서 보존). DCA도 같은 원장 상한 대상이다(전 전략 공통; DCA는 `fitBuysToBudget` override가 없어 한도 초과 시 BUY 전체 거절). 주식 DCA 계획 단계(`DcaPlanInputCollector`)도 브로커 잔고·판매가능수량·매수가능금액을 조회하지 않는다(`SellableQuantityPort`·`UNLIMITED_CASH` 제거, MOCK 포함 동일): BUY 상한 = 위 `remaining`(부족 정책 PARTIAL|REJECT 적용, 같은 배치 앞 규칙 BUY 차감), SELL 상한 = 원장 보유 − 같은 사이클·거래일 기존 SELL − 리포트 전 접수 후 취소된 당일 SELL의 기록된 체결분(모르면 주문 수량), 0 하한(원장 없으면 DATA_UNAVAILABLE "원장 조회 실패" skip). 계좌 미배정 현금(`UnassignedCashCalculator` — 주식 USD 매수가능금액 − 계좌 전략 원장 예수금 합)은 DCA 원장 예수금도 뺀다. 증권사와 원장의 어긋남은 미리보기 `accountHoldingsCheck` 경고와 접수 단계 SELL 거절 사용자 알림("보유 수량 부족")이 신호다. 계좌 간 병렬화는 `TradingCandidatePlanner`가 계좌별 태스크를 `TradingParallelRunner`로 묶고(`batchGuard.runSafely`로 격리), 계좌 내부 판정~PLANNED 커밋은 `AccountBudgetLock`으로 직렬화한다. 신규 BUY가 원장을 넘어 전부 거절되고 기존 주문도 없는 사이클은 접수·포지션 저장·리포트에서 제외하고 `InsufficientBalanceEvent`(사용자 알림)를 낸다. 미리보기(`TradingPreviewService`)만 계좌 단위 `accountCashCheck`(증권사 `MarginPort.getUsdBuyableAmount` 1회 조회, 경고 전용)와 (계좌, 종목) 단위 `accountHoldingsCheck`(`SellableQuantityPort` 종목당 1회 조회, 경고 전용 — 판매 가능 수량은 미체결 매도 차감 전 보유 수량이라 필요량에 PLACED SELL도 포함)를 내며 배치 판정에는 쓰지 않는다.
- `BuyOrderPriceCapper.buildCappedBuyOrders`(INFINITE)는 재진입(같은 close 배치 내 접수 직전 재조회 가격이 최초 계산 시점보다 추가로 하락해 캡이 다시 트리거되는 경우) 시 입력에 이미 `INFINITE_CORRECTION_*` leg가 섞여 있으면 base 주문(평단가/기준가)만 추출해 재산정한다 — correction leg를 base로 오인해 잘못 계산하는 것을 방지.
- 계좌별 브로커 토큰: Meritz는 `broker_tokens` 테이블에 account_id(PK) 기준 독립 관리 (`BrokerTokenEntity`), Toss 계좌·관리자 토큰은 Redis canonical hash에 공유 (`TossDistributedTokenCoordinator` + `TossRedisTokenStore`)
- **시세 출처 — 값 하나에 출처 하나, 다른 출처로 넘어가는 폴백 없음**:

  | 값 | 출처 | 쓰는 곳 |
  |---|---|---|
  | 주문 경로의 현재가 | 계좌 증권사(`BrokerPricePort.currentPrices`, 계좌 토큰). Mock 계좌는 증권사가 없어 공용 시세, 토스 계좌는 임시로 공용 시세(`vendors/toss.md`) | 개장·마감 배치의 계획·접수(`TradingPriceFetcher`, 가격 키 `PriceKey(계좌, 종목)`), 수동 실행(`ManualTradingService`), VR 재설정(`VrReconfigureService`) |
  | 전일 종가 | 공용 시세(Alpaca `latestCloses`) | 배치 계획(INFINITE 0회차, DCA 기준가·조건), 미리보기, 등록, 통계 `GET /prices` |
  | 확정 종가·일봉 | 공용 시세(`requireConfirmedClose`·`confirmedBars`·`dailyCandles`) | 마감 리포트, VR 롤오버, Mock 체결 판정, 차트, DCA 지표, 백테스트 |
  | 화면의 현재가 | 공용 시세(`latestPrices`, 60초 캐시) | 원장 합산(`AccountLedgerTotalsService`), Mock 잔고 |

  배치는 계좌별로 그 계좌 전략의 종목만 병렬 조회한다(`selectPriceAccount`·관리자 시세 체인은 없다). 한 계좌의 현재가 조회가 실패하면 그 계좌의 그 종목 전략만 빠지고 관리자 알림은 배치당 1건(`TradingErrorEvent`)이다. 전일 종가 조회가 실패하면 그 계좌의 현재가로 대신한다. **확정 종가 없음 → 리포트 보류**: 마감 리포트는 마감 20분 뒤(05:20/06:20 KST, 조기 마감일 closeAt+20)에 돌고, 접수 대상 종목의 확정 종가가 없으면 10분 뒤 빠진 종목만 한 번 재조회한다(정상 마감 경로만). 그래도 없으면 그 종목의 전략은 리포트하지 않고 CLOSE 단계를 DONE으로 남기지 않으며(PLACED 유지) `[마감 리포트 보류] [TQQQ] 확정 종가 없음 — 매시 정각 5분에 리포트를 다시 시도합니다` 알림을 1건 보낸다. `TradingCloseScheduler.reconcile()`(매시 :05)이 PLACED 단계의 리포트를 closeAt+40분(`REPORT_RETRY_AFTER`)부터 `tryRun`으로 다시 돌리고 재기동 재개도 같은 경로이며, KST 자정을 넘기면 멈춘다. 알려진 한계: 보류 알림이 자정까지 매시 반복되고, 보류일에도 heartbeat는 핑한다. 단일 값 조회 실패는 `tryGet`, 중단이 필요한 등록·롤오버는 `wrap`이다.
