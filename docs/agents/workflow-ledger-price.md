# 전략 원장 상한·시세·브로커 토큰

배치 실행 순서는 workflow-batch.md("스케쥴러 실행 흐름").

## 스케쥴러 실행 흐름 — 원장 상한·시세·토큰
- 전략별 원장 상한: 각 전략은 자기 원장(`cycle_position.usd_deposit`) 안에서만 BUY를 낸다 — `StrategyLedgerBudget`(`applies`/`remaining`/`fit`)이 배치·수동 실행·재주문·접수 직전 재캡의 공용 판정이다. `remaining(cycle, tradeDate)` = 최신 원장(첫 거래일처럼 `cycle_position`이 없으면 `StrategyCycle.startAmount()`) − 같은 날 이미 저장된 BUY(PLANNED·SUBMITTING·PLACED) 금액과 마감 리포트 전 CANCELLED BUY의 기록된 체결분(`unreportedCancelledBuys`·`pendingCancelledFill` — 체결량을 모르면(`filledQuantity` null) 주문 금액 전체)을 한 번만 차감한 값이다(신규 후보는 `TradingOrderSlots.excludeExisting`으로 이미 저장된 슬롯을 뺀 뒤 판정해 이중 차감이 없다). `fit`은 BUY 총액이 한도를 넘으면 `fitBuysToBudget`으로 1회 축소하고(INFINITE=보정 생략, VR=싼 단부터 절단, PRIVACY=축소 없음) 그래도 못 담으면 BUY 전체를 제거하며 SELL은 항상 유지한다(후보 내부 원래 순서 보존). DCA(`occupiesSeed()=false`)는 원장 상한 제외다. 계획 단계는 주식 DCA BUY만 예외로 브로커 매수가능금액을 읽는다(코인 BUY처럼 부족 정책 PARTIAL|REJECT 적용 — 가용 USD = `MarginPort.getUsdBuyableAmount` − 같은 계좌 시드 점유 전략 원장 합 − 자기 PLANNED·SUBMITTING BUY − 같은 배치 앞 규칙 BUY, `UnassignedUsdCalculator`; MOCK·US 주식 외는 상한 없음, 조회 실패는 DATA_UNAVAILABLE skip). 주식 DCA SELL도 예외로 브로커 판매가능수량을 읽는다(SELL 규칙이 처음 필요할 때 전략당 1회; 상한 = min(원장 보유 − 같은 사이클·거래일 기존 SELL − 리포트 전 접수 후 취소된 당일 SELL의 기록된 체결분(모르면 주문 수량), `SellableQuantityPort` 판매가능 − 같은 계좌·종목 당일 PLANNED/PLACED SELL 합), 0 하한; MOCK·US 주식 외는 원장만, 조회 실패는 DATA_UNAVAILABLE "판매가능수량 조회 실패" skip). 그 외 시드 전략(INFINITE·VR·PRIVACY)은 위 원장 원칙 그대로 브로커 live 잔고·판매가능수량을 조회하지 않는다. 증권사와 원장의 어긋남은 미리보기 `accountHoldingsCheck` 경고와 접수 단계 SELL 거절 사용자 알림("보유 수량 부족")이 신호다. 계좌 간 병렬화는 `TradingCandidatePlanner`가 계좌별 태스크를 `TradingParallelRunner`로 묶고(`batchGuard.runSafely`로 격리), 계좌 내부 판정~PLANNED 커밋은 `AccountBudgetLock`으로 직렬화한다. 신규 BUY가 원장을 넘어 전부 거절되고 기존 주문도 없는 사이클은 접수·포지션 저장·리포트에서 제외하고 `InsufficientBalanceEvent`(사용자 알림)를 낸다. 미리보기(`TradingPreviewService`)만 계좌 단위 `accountCashCheck`(증권사 `MarginPort.getUsdBuyableAmount` 1회 조회, 경고 전용)와 (계좌, 종목) 단위 `accountHoldingsCheck`(`SellableQuantityPort` 종목당 1회 조회, 경고 전용 — 판매 가능 수량은 미체결 매도 차감 전 보유 수량이라 필요량에 PLACED SELL도 포함)를 내며 배치 판정에는 쓰지 않는다.
- `BuyOrderPriceCapper.buildCappedBuyOrders`(INFINITE)는 재진입(같은 close 배치 내 접수 직전 재조회 가격이 최초 계산 시점보다 추가로 하락해 캡이 다시 트리거되는 경우) 시 입력에 이미 `INFINITE_CORRECTION_*` leg가 섞여 있으면 base 주문(평단가/기준가)만 추출해 재산정한다 — correction leg를 base로 오인해 잘못 계산하는 것을 방지.
- 계좌별 브로커 토큰: KIS는 `broker_tokens` 테이블에 account_id(PK) 기준 독립 관리 (`KisTokenEntity`), KIS 관리자(시세 전용) 토큰은 Redis `kis:admin:token:<sha256(appKey) 앞 8자>`(`KisAdminTokenCoordinator`, Redis 장애 시 JVM 메모리 폴백 — `broker_tokens`는 accounts FK라 쓸 수 없음), Toss 계좌·관리자 토큰은 Redis canonical hash에 공유 (`TossDistributedTokenCoordinator` + `TossRedisTokenStore`)
- **시세 출처 — 관리자 시세 우선**: 배치 시세는 ① Toss 관리자(`/api/v1/prices`·일봉 캔들) → ② KIS 관리자(`KIS_ADMIN_APP_KEY`/`KIS_ADMIN_APP_SECRET`, 미설정이면 건너뜀) → ③ 배치 계좌(`selectPriceAccount` — Toss 계좌 우선) 순으로, 앞 단계에서 빠진 종목만 다음 단계로 넘긴다(①② = `AdminMarketPricePort`/`AdminMarketPriceAdapter`, 단계별 warn 로그만). 현재가·전일종가·확정 종가 모두 `BrokerRouter.getPrice(s)`·`getPrevClose(s)`·`getClosingPrice(s)`가 체인을 건다(`TradingPriceFetcher`는 라우터 결과의 누락분만 단건 폴백) — 그래서 미리보기·전략 생성 기준가·통계 `GET /prices`·VR 롤오버 확정 종가·수동 주문 cap 판단(`ManualTradingService`)·`VrReconfigureService` 현재가도 같은 출처다(`getPriceSnapshot(s)`는 프로덕션 소비처가 없어 계좌 어댑터 전용 유지). 다건 메서드는 계좌 보충 조회가 실패해도 관리자 결과가 1건 이상이면 warn 로그 후 부분 결과를 반환하고(누락 종목은 호출부 처리), 관리자 결과가 비어 있으면 예외를 그대로 전파해 503/422/429를 보존한다(단건은 항상 전파, 인증 예외(422)는 사용자 조치 신호라 관리자 결과가 있어도 전파, 호출 한도(429)는 일시 오류라 부분 결과 우선). 세 단계 모두 실패한 종목만 `TradingErrorEvent` 1건. ①②는 대체값을 쓰지 않는다(캔들 실패를 현재가로, KIS `last` 빈값을 `base`로 메우지 않음) — 대체는 ③ 계좌 어댑터만. 결과적으로 KIS 계좌만 있는 배치도 시작가·`BuyOrderPriceCapper` cap·DCA 기준가가 Toss `lastPrice`(확장시간 체결가 포함)를 쓴다. 알려진 한계: (a) Toss 캔들 실패 시 개장 전 배치는 KIS 관리자 `base`(D-2 종가일 수 있음)를 전일종가로 쓴다 — 드문 장애 경로라 수용, warn 로그로 감지 (b) MOCK 계좌는 라우터 종가(Toss 실패 시 KIS 관리자)와 `MockBrokerAdapter` 내부 체결 판정 종가(`TossPriceApi` 공통 시세, Toss 실패 시 라이브가)가 Toss 캔들 실패일에 다를 수 있다 — 의도된 수용
